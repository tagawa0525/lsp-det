# ADR 0001: 仕様先行ではなくツール先行とし、v0.1 は readiness ゲートに絞る

- 日付: 2026-08-28
- 状態: 採用

## 経緯

本プロジェクトは当初「LSP Deterministic Extensions 仕様草案 v0.1」（現 [vision.md](../vision.md)）として始まり、3 拡張（A: 宣言範囲、B: 準備完了、C: 起動マニフェスト）の仕様・準拠テスト・参照プロキシを一体で提供し、LSP 本体への提案を最終目標としていた。実装着手前の設計検討（2026-08-27〜28）で以下を確認した。

- 標準化は年単位の活動である。準備完了の標準化提案（LSP issue #511）は 2018 年から未解決のまま
- solidlsp（Serena）の言語別フックの実測では、補正コストは起動・初期化系（78/75/75 件）≫ 準備完了の固定待ち（14 件）> 範囲補正（8〜10 件）。草案が筆頭に置いていた拡張 A の実害は相対的に小さい
- 現行のコーディングエージェント（Claude Code 含む）は編集を文字列置換で行い、LSP の range を切り貼りに使わない。一方 Claude Code は definition / references / documentSymbol / callHierarchy をネイティブに使うため、インデックス未完了時の空応答の誤認は直接の実害がある
- 体制は一人・週 20h。仕様・準拠テスト・5 言語のプロキシを並行で維持する分量ではない

## 決定

1. **ツール先行**: プロキシを実用ツールとして先に完成させ、自分の環境（Claude Code + Serena）で実証する。仕様文書と上流提案は安定稼働後に再評価する。成功基準は「自分で便利に使えること」
2. **v0.1 は拡張 B（準備完了）のみ**: readiness ゲート付き透過プロキシを作る。拡張 A は除外（tree-sitter 等パーサ同梱の判断ごと延期）。拡張 C は argv 指定に縮退し、マニフェスト・レジストリ・インストーラは作らない
3. **ゲートは遮断方式**: 無改造クライアントは `workspace/readiness` を呼ばないため、注釈方式（`$partial`）では初日の価値がない。ワークスペース横断リクエストを ready まで保留する遮断が唯一効く。再インデックス中も保留し、タイムアウトは非常口とする
4. **ready 判定はサーバー別ヒューリスティック**: rust-analyzer は `experimental/serverStatus`、gopls は `$/progress`（title "Setting up workspace"）。将来は各言語サーバー本体に判定を取り込ませる PR を目指す
5. **対応言語は rust-analyzer + gopls の 2 つ**: 作者の使用言語と、「機械可読な readiness を持つ／持たない」の対照で選定
6. **起動指定は argv 完結**: 起動コマンドは呼び出し側の設定ファイル（`.lsp.json` / `ls_args`）に常在させることで再現性を担保する。プロキシ独自の設定ファイルは暗黙の探索が非決定性の入口になるため持たない。必要になれば `--config <明示パス>` のみ許可

## 影響

- v0.1 の分量が「透過プロキシ + アダプタ 2 つ」まで縮み、週 20h で数ヶ月内に日常投入できる見込みになった
- 多重化・capability マージ・ID 書き換え（ra-multiplex の難所）を非目標として明示的に回避する
- vision.md の 5 章（上流提案経路）と 6.7（標準化用調査）は凍結。再開判断は v0.1 の安定稼働後
