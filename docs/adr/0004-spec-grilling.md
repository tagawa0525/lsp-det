# ADR 0004: 拡張 S 仕様の精査で確定した設計判断

- 日付: 2026-08-29
- 状態: 採用
- 関連: [ADR 0003](0003-extension-s-zero-based.md)

## 経緯

拡張 S 仕様（v0.1 草案）を対象にした設計精査で、以下の欠陥・曖昧さが見つかった: (1) `health` × `readiness` の組み合わせの意味が未定義、(2) `dead` はサーバーが送出できない値なのに送出主体が仕様に書かれていない、(3) 完全性の保証が強すぎて準拠できるサーバーが存在しない疑い（clangd は全インデックスを持たず、tsserver は非同期）、(4) 鮮度の保証を参照実装（プロキシ）自身が gopls アダプタで守れるか不明、(5) メソッド名が LSP 標準名前空間（`workspace/`）を受理前に占有、(6) クライアントの capability 宣言に「通知が欲しい」と「保護が不要」の 2 つの意味が混在。

## 決定

1. **2 軸は独立のまま維持**し、「`health` が `error | dead` のとき `readiness` を判断に使うべきではない」を非規範の推奨解釈として記載する。行列で厳密に縛らない（情報を多めに渡すこと自体は害ではない）
2. **`dead` は仕様に残し、送出主体の表で層を分ける**: サーバーは送出してはならず、中継層のみ送出できる。定義が必要な理由は、送出者（lsp-det 等の中継層）と受信者（クライアント）の共通語彙になるため。上流提案時に位置づけを再検討する旨を仕様に明記
3. **保証にグレードを導入する**: `serverStateProvider` capability を `boolean | { completeness?, freshness? }` とし、実装が守れる保証だけを宣言する。enum（段階）ではなく独立 boolean を採る — completeness と freshness は直交し、現実のサーバーが 4 象限すべてに存在する（rust-analyzer: 両方 / tsserver: completeness のみ / clangd: freshness のみ / 基本グレード）。completeness の対象メソッドは仕様側で固定列挙し、サーバーごとの可変リスト（旧 `completeMethods`）は復活させない
4. **メソッド名は受理まで `experimental/` プレフィックス**（`experimental/serverState` / `experimental/serverStateChanged`）。LSP 本体取り込み時に `workspace/` へ改名
5. **クライアント宣言の意味を仕様で一義化する**: `experimental.serverState: true` は「状態を自分で解釈し、待つか進むかを自分で判断する意思表示」。よって宣言 = ゲート自動解除は 1 つの意味しか持たず維持できる（ADR 0002 の決定 3 を仕様の明文化で補強）。待つか進むかの判断はクライアントの権利であり責任である、という設計哲学を仕様 1 章に明記
6. **ゲートに動作モードを追加**: 既定は保留（`--gate-mode hold`）。「正直なエラーを即返し判断をクライアントに委ねる」`--gate-mode error` を用意するが、クライアントがエラーを握りつぶして空結果化する実例（vscode-languageclient）があるため既定にしない。CC のエラー表示を M2 で実測してから既定を再判断する
7. **準拠テストスイートを独立成果物に格上げ**: M2 の中心成果物は「仕様 7 節を実行可能にしたスイート + それに合格するプロキシ」。スイートは実サーバーにも適用できる形で書き、上流提案の説得材料とする（元草案の設計原則「準拠テストが本体」の復権）

## 影響

- 仕様は「準拠可能性」を回復した: 保証を宣言制にしたことで、clangd のような部分実装にも参加の道があり、嘘の宣言だけが違反になる
- プロキシのアダプタは上流ごとに宣言を変える: rust-analyzer は completeness + freshness（M2 で実測確認）、gopls は completeness のみ（freshness は M3 実測後）
- 実測項目が 2 つ増えた: CC のエラー表示挙動、rust-analyzer / gopls のスナップショット方式の確認
