# ADR 0005: 実行モデルは std スレッド、tokio・rayon・tracing は採用しない

- 日付: 2026-08-29
- 状態: 採用

## 経緯

M1 実装の入り口として、非同期ランタイム（tokio）か std スレッドかを検討した。ユーザーは tokio / tracing / serde / thiserror / rayon を「実質標準ライブラリ」とみなす立場だが、依存削減にも価値を認めており、CPU を使い切る余地（並列化）を残すかも論点になった。

## 決定

**実行モデル**: std スレッド 3 本（クライアント読み・上流読み・子プロセス監視）+ `mpsc` チャネル + 単一イベントループ。タイマー（ゲートの非常口）は `recv_timeout` で実現する。

**採用する依存**（3 つ）:

- `serde` / `serde_json` — JSON の覗き見（`RawValue` で method / id のみ読み、ボディは非破壊）と拡張 S メッセージの生成に必須
- `thiserror` — エラー型の定型削減。コンパイル時のみのコスト
- `libc` — `PR_SET_PDEATHSIG`（親死亡検知）に必要

## 採用しなかったもの（理由付き）

| 候補 | 不採用の理由 | 再検討の条件 |
| --- | --- | --- |
| tokio | 接続は常に固定 2 本 + 子プロセス監視で、非同期ランタイムが正当化される「多数接続の多重化」が存在しない（ra-multiplex/lspmux は TCP で N クライアントを受けるため tokio が正解だった）。tokio の stdin/stdout は内部的にブロッキングスレッドのラッパーであり、stdio 中心の本ツールでは水面下の動作が std 案と同じになる。テストの決定性に `#[tokio::test]` / `time::pause` 等の機構が増える | socket transport 対応、または多重化（現在は明示的な非目標）をやるとき。I/O 供給部とイベントループは分離されているため載せ替えは可逆 |
| rayon | 並列化する計算が存在しない。重い計算（インデックス・解析）はすべて言語サーバー側で起き、プロキシはバイト転送のみ。さらに LSP はメッセージ順序が意味を持つ（didChange の順序が狂えば文書状態が壊れる）ため、メッセージ処理の並列化は性能改善ではなく正しさの破壊になる | プロキシ内に CPU バウンドな処理（例: 拡張 A の範囲合成）を持つことになったとき |
| tracing | v0.1 のログは stderr への逐次書き出し（prefix 付き、即時フラッシュ）で足りる。構造化ログ・スパンが必要な複雑さがまだない | ログの相関（リクエスト ID 追跡等）が実際に必要になったとき。後付けは容易 |
| 設定ファイル | ADR 0004 以前に決定済み（argv 完結、暗黙の探索禁止） | フラグが 1 行に収まらなくなったら `--config <明示パス>` のみ許可 |

## 影響

- 依存ツリーが最小になり、ビルドが速く、supply chain 面積が小さい
- イベントループは同期の純関数としてテストできる（イベント列 → 出力列。ランタイム制御の機構が不要）
- 「CPU を使い切る」設計余地は意図的に持たない。プロキシのスループット上限はパイプ I/O と上流サーバーであり、プロキシの CPU ではない
