# ADR 0006: 外部レビュー指摘による仕様・設計文書の補正

- 日付: 2026-08-28
- 状態: 採用（**決定 3 の前提は誤り**。実測により [ADR 0007](0007-quiescent-flap-measured.md) が訂正）
- 関連: [ADR 0001](0001-tool-first-readiness-gate.md)、[ADR 0003](0003-extension-s-zero-based.md)、[ADR 0004](0004-spec-grilling.md)

## 経緯

仕様・ADR 一式への外部レビュー（2026-08-28）で以下の指摘を受けた。(1) ADR 0001 決定 1（ツール先行、仕様は安定稼働後）と ADR 0003 決定 7（仕様が第一の成果物）が矛盾したまま並んでおり、実装中に「仕様の都合」と「使い勝手の都合」が衝突したときの裁定基準が二重になっている。(2) freshness の準拠テスト（仕様 7.3）が単一ファイルの変更→問い合わせだと、LSP の既存の処理順序保証（同一接続では後続リクエストが先行通知の後に処理される）で通ってしまい、何も検証しない。(3) rust-analyzer は通常編集でも `quiescent: false` に戻るため、既定の `--gate-mode hold` では編集のたびに横断リクエストが保留される可能性があるが、設計 4.3 はブランチ切り替え等しか想定していないように読める。(4) `experimental/serverState` と rust-analyzer の `experimental/serverStatus` が名前として近く、ログや設定で混同しやすい。(5) `process.rs` の `PR_SET_PDEATHSIG` は Linux 専用だが、macOS 未対応がどこにも明示されていない。(6) CLAUDE.md の「GitHub リモート未設定」が古い。

> **訂正（2026-08-29）**: 以下の段落の内容は誤りである。実測により否定された（[ADR 0007](0007-quiescent-flap-measured.md)）。当時の記述をそのまま残すのは、誤りの内容と、それを「ソースで確認した」と書いてしまった経緯を記録に留めるため。

指摘 (3) は rust-analyzer のソースで確認した: `quiescent` の実体は `is_fully_ready()`（ワークスペースロード完了かつキャッシュプライミング非実行、`reload.rs`）であり、ディスク上のファイル変更は VFS 再ロード（`vfs_done: false`、`main_loop.rs`）と再クワイエセンス時のプライミング再実行を引き起こす。Claude Code は編集をディスク書き込みで行うため、編集のたびに `quiescent` が `false → true` を往復しうる。純粋なインメモリの `didChange` だけでは往復しない。

指摘 (5) も確認した: `cfg(unix)` ガード下で `libc::PR_SET_PDEATHSIG` を参照しており、macOS では `cfg(unix)` が真なのにこの定数が存在しないため、ビルド自体が通らない。

## 決定

1. **ADR 0001 と ADR 0003 の優先関係を裁定する**: ADR 0003 決定 7 が ADR 0001 決定 1 を一部改訂する。両立解釈は「仕様が正だが、v0.1 の仕様はツールとして成立する範囲に絞る」。実装中に仕様の都合と使い勝手の都合が衝突した場合は、仕様を実装の都合で曲げず、報告して仕様側の改訂判断を仰ぐ（CLAUDE.md の既存ルールと同じ運用）。ADR 0001 の「成功基準は自分で便利に使えること」はツールの成功基準として存続する
2. **freshness の準拠テスト（仕様 7.3）はクロスファイル必須とする**: ファイル A を変更した後、別ファイル B を起点とする横断問い合わせが A の変更を反映することを検証する。単一ファイル内の変更→問い合わせは LSP の処理順序保証だけで満たされてしまい、freshness を検証しない
3. ~~**rust-analyzer の通常編集による quiescent フラップを設計 4.3 に記載し、M2 の実測項目に加える**~~: フラップの頻度・保留時間・体感影響を実測してから対策の要否を判断する。実測前に平滑化等の対策を設計しない（最小実装の原則）。→ **前提が誤りだった**。2026-08-29 の実測で、通常編集では `quiescent` が往復しないことが判明した（[ADR 0007](0007-quiescent-flap-measured.md)）。「実測してから判断する」という手順自体は正しく機能し、その結果この決定の前提を破棄した
4. **命名は維持し、仕様 8 章に混同注意を明記する**: `experimental/serverState` が `experimental/serverStatus` と近いのは後継であることを示す意図的な命名。上流提案時に後継関係を明示する。**同名再利用（`experimental/serverStatus` の流用）は却下**: (a) ペイロード非互換 — `quiescent` の消失は Serena の ready 判定（`params.get("quiescent") is True`、失敗時 120 秒タイムアウト）を壊し、`health` の新値 `dead` は Zed の enum デシリアライズを壊しうる。(b) 中継層は上流の本物の `serverStatus` を原文のまま透過しなければならない（握りつぶすと Serena の起動が壊れる）ため、同名だと同一接続上に schema・送信者の異なる通知が 2 系統流れて判別不能になる。別名なら共存できる。(c) capability 契約が別物（購読フラグのみ vs リクエスト + 通知 + 保証グレード宣言）。この却下は中継層が存在する構成では恒久的であり、再検討しない
5. **v0.1 の対応 OS は Linux のみと明示する**: `PR_SET_PDEATHSIG` は Linux 専用で、現行実装は macOS ではビルドできない。macOS 対応（kqueue の `EVFILT_PROC` 等による親死亡検知）は v0.1 後の課題として非目標に記載する。コードの `cfg(unix)` は当面変更しない — macOS でビルドエラーになるのは「pdeathsig なしで静かに動く」より正直な失敗である
6. **文書を現状に同期する**: GitHub リモート（`github.com/tagawa0525/lsp-det`）は作成済み。CLAUDE.md と設計 10 章を PR フロー前提の記述に更新する

## 影響

- 仕様 7.3 が厳密化され、準拠テストスイート（M2）の freshness テストはクロスファイル fixture が必須になる
- M2 の実測項目に「通常編集による quiescent フラップの頻度と保留時間」が加わる。結果次第で `--gate-mode` の既定やフラップの扱いを再判断する
- v0.1 の対象プラットフォームが Linux のみであることが明文化され、macOS ユーザーへの提供は将来課題として追跡される
- 以後の開発は feature ブランチ + PR + レビュー待ちフローに従う
