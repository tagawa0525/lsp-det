# ADR 0007: 通常編集で quiescent は往復しない（ADR 0006 決定 3 の前提を訂正）

- 日付: 2026-08-29
- 状態: 採用
- 関連: [ADR 0006](0006-external-review-fixes.md)、[実測](../research/rust-analyzer-quiescent-measurement.md)

## 経緯

ADR 0006 決定 3 は「rust-analyzer は通常編集（ディスク書き込み）でも `quiescent` が `false` に
戻るため、既定の `--gate-mode hold` では編集→横断リクエストの連打で毎回保留が入りうる」とし、
頻度と保留時間の実測を M2 の宿題とした。

M2 で実測した（[docs/research/rust-analyzer-quiescent-measurement.md](../research/rust-analyzer-quiescent-measurement.md)）。
結果は前提を否定した。ソースファイルへのディスク書き込みでも `didChange` でも `quiescent` は
一度も `false` にならず、インデックスへの反映は 0.02〜0.04 秒で完了していた。陽性対照として
`Cargo.toml` を変更すると期待どおり往復したため、測定系の不備ではない。

前提が誤っていた原因は、ADR 0006 執筆時に `is_quiescent()` が `vfs_done` を見ていることだけを
確認し、`vfs_done` を何が動かすかを確認しなかったこと。`vfs_done` は VFS の一括ロード進捗でのみ
更新され、個別ファイルの変更では動かない。キャッシュのプライミングも `quiescent` が `false` から
`true` へ移る辺でしか要求されない。

## 決定

1. **ADR 0006 決定 3 の前提を破棄する**。通常編集で `quiescent` は往復しない。往復するのは
   ワークスペース構成の変更（`Cargo.toml`、ブランチ切り替え等）のみで、これは v0.1-design 4.3 が
   元から想定していた条件である。同節に加えた「通常編集でも起きる」旨の記述を実測に置き換える
2. **フラップ対策は実装しない**。平滑化・デバウンス・保留の猶予時間はいずれも不要。
   対策の要否を実測後に判断するとした ADR 0006 決定 3 の手順に従った結果である
3. **`--gate-mode hold` を既定のまま維持する**。編集→横断リクエストの連打が保留される懸念は
   実測で否定された。既定の再判断材料は CC のエラー表示の実測（ADR 0004 決定 6）のみとする
4. **測定値の一般化を禁じる**。「往復しない」は `is_fully_ready()` の入力に通常編集が触れない
   という構造由来の性質であり規模に依らない。一方「往復したときの保留時間」（本測定では 250ms）は
   ワークスペース規模に依存するため、大規模プロジェクトの根拠に使ってはならない
5. **文書化されていない推論を確認済みとして書かない**。ADR 0006 決定 3 は、ソースの一部だけを
   読んだ推論を「ソースで確認した」と記述していた。以後、コードの挙動を根拠にする場合は
   その挙動を駆動する側まで辿るか、推論であることを明示する

## 影響

- v0.1-design 4.3 を実測に合わせて訂正する。M2 の実測項目からフラップ計測を落とす（完了のため）
- ゲート実装（M2 の次の PR）はフラップを考慮しなくてよくなり、単純になる
- 副産物として次の 2 点が実地検証された: capability 注入（設計 4.5）が実 rust-analyzer に効くこと、
  M1 の未検証項目だった実サーバーとの結合が成立すること
- rust-analyzer の freshness 宣言（仕様 8 章「要実測確認」）の根拠が一つ増えた。ただしこれは
  `workspace/symbol` 1 メソッドでの確認であり、宣言の最終判断は準拠テストスイート（仕様 7.3 の
  クロスファイル鮮度テスト）の結果を待つ
