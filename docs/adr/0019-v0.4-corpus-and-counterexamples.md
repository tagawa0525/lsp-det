# ADR 0019: 0.4.0 は語彙のコーパスと反例の実サーバーでの検証、0.5.0 は易しい 4 サーバー

- 日付: 2026-09-06
- 状態: 採用
- 関連: [ADR 0018](0018-external-review-2026-09.md) 決定 A-5・C・D、[ADR 0010](0010-python-typescript-mappings-for-client-adoption.md)（v0.2 の範囲の決め方）、[ADR 0009](0009-success-criterion-and-two-sided-reference.md) 決定 C-4（時間判定の排除）・D-5（保証は測った版に）、[research/serena-solidlsp.md](../research/serena-solidlsp.md) 1.2、[research/external-review-2026-09.md](../research/external-review-2026-09.md) §6

## 経緯

外部レビュー（ADR 0018）の §6 は、Serena の 30 言語の待ち方が「初回のワークスペース走査が終わったか」の 1 ビットに潰れることを根拠に readiness の 1 軸は硬くしてよいとしつつ、硬くする前に当てるべき反例を挙げた。Metals（progress の end の後に 3 秒の静穏期間）、Erlang（ログ + progress + 落ち着き待ち）、Nextflow（references のたびに明示同期するリクエスト単位の鮮度モデル）、Haxe（キャッシュがあれば最初から ready）、AL（通知ではなくリクエストのポーリング）、Vue / Svelte / Angular（相方の TS サーバーとの合成）である。

外部に出すまでは理想を追い根源的に解く方針（ADR 0018 決定 D）なので、語彙が動く可能性のある検証を先に済ませ、動かないと分かった語彙に易しいサーバーを当てる。順序を逆にすると、語彙が動いたときに易しいサーバーの写像まで書き直すことになる。

## 決定

### A. 範囲

1. **0.4.0** は、Serena の 30 言語を本プロトコルの語彙に写す机上コーパス（ADR 0018 決定 A-5）と、コーパスで「写像に疑問」が付いた言語の実サーバーでの検証である。仕様と語彙が動くならここで動かし、既存の写像・準拠テスト・fork のパッチを追従させる。変えない理由を手戻りの大きさに求めない
2. **0.5.0** は、固まった語彙に易しい 4 サーバー（Dart analysis server、Sorbet、jdtls、clangd）を当てる。着手時に別の ADR で範囲を書く。Sorbet は nixpkgs にないので、rubygems の `sorbet-static`（x86_64-linux の prebuilt。NixOS で glibc 以外に依存せず動くことを確認済み）を `flake.nix` の derivation として取り込む
3. 外部へのアクションは 0.5.0 の後（ADR 0018 決定 D）

### B. 検証する言語の選び方

1. コーパスの各行は、Serena の手段ではなく**そのサーバー自身の文書とソース**で信号の有無と意味を確かめてから埋める（ADR 0018 決定 C）
2. 「写像に疑問」が付いた行の言語を実サーバーで検証する。数に上限は置かない
3. 出発点の見込みは Metals、Elixir（`$/progress` "Building"）、Kotlin（progress の後の安全バッファ）、Nextflow（リクエスト単位の同期）。いずれも nixpkgs にあるか（metals、elixir-ls、kotlin-language-server）、jar を `fetchurl` で取れる（Nextflow の言語サーバー）
4. 入手に手間がかかる言語（Erlang LS は nixpkgs になく rebar3 で自前ビルド、Haxe の言語サーバーは vshaxe の release、AL は VS Code 拡張の同梱で単体入手できない）は、疑問の中身が別の言語で既に検証できるなら重複として省く。省いた理由はコーパスの行に書く
5. 相方サーバーとの合成（Vue / Svelte / Angular）は、2 つの lsp-det で挟んで**測定だけ**する。合成はサーバー 2 つを起動すると決めたクライアントの責務であり、接続ごとの `ServerState` を AND すれば足りる。lsp-det は隣の接続を知らず、知るべきでもない（上流 1 つ、argv 完結、設定ファイルなし）。「接続ごとの保留で結果が完全になる」を Vue（または Svelte）で確かめ、成り立てば research に記録して vision に書く。成り立たない事例が出たときだけ仕様の変更を ADR で検討する

### C. 検証の中身

各言語は pyright / typescript-language-server と同じ段階を踏む。`flake.nix` にサーバーを足す → 実測記録（research、既存の `*-measurement.md` と同じ形式）→ 写像を RED → GREEN → REFACTOR → 実サーバーの結合テスト（7.1 / 7.2 / 7.3、`#[ignore]`）→ `TESTED_VERSIONS`。

検証の結果として **`unknown` も正しい答え**である。時間を使わずに `ready` を言えないサーバー（progress が常に何か走っているなど）の正直な写像は両軸 `unknown`、または `indexing` に長く留まることであり、それを「写像できなかった」と数えて時間判定を持ち込まない（ADR 0009 決定 C-4）。方針の見直しは試してから考える。

### D. devShell の分け方

`flake.nix` の `devShells.default` は lsp-det をビルドする道具だけ（rustc、cargo、clippy、rustfmt）にし、言語サーバーは今の 4 つも含めて `devShells.servers` に置く。準拠テストの実サーバー結合とドッグフーディングは `servers` で行い、作者の `.envrc` は `use flake .#servers` にする。境目を「今の 4 つ」に置く理由がないので、default には 1 つも置かない。

### E. マイルストーン

- **M8 — コーパス**: research の新しい文書。1 言語 1 行。下書きは機械的なので Sonnet に任せ、行ごとにサーバー自身の資料で確かめる（決定 B-1）
- **M9 — Metals**、**M10 — Elixir**、**M11 — Kotlin**、**M12 — Nextflow**: 決定 C の段階。コーパスで疑問が付かなかった言語は M から外し、疑問が付いた別の言語は追補で M13 以降に足す
- **M13 — 相方サーバーとの合成の測定**: 決定 B-5
- **M14 — devShell の分割**: 決定 D。M9 より前に行う

### 却下した案

| 案                                                                           | 却下理由                                                                                                  |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 易しい 4 サーバーを先にする                                                  | 語彙が動いたときに書き直しになる                                                                          |
| 反例と易しい 4 つをまとめて 0.4.0 にする                                     | 易しい 4 つは固まった語彙に当てたい                                                                       |
| 反例のサーバーは `readiness` の写像だけにして保証と `TESTED_VERSIONS` を省く | 保守は線形で問題ない（ユーザー判断）。同じ段階を踏む                                                      |
| 相方サーバーとの合成の規則を仕様に入れる                                     | 決定 B-5。クライアントの責務で、サーバーの義務（3〜7 章）に入らず、lsp-det も代行できないしすべきでもない |
| Erlang LS を最初から自前ビルドで入れる                                       | 決定 B-4。疑問の中身（落ち着き待ち）が Metals で検証できるなら重複                                        |
| default の devShell に今の 4 サーバーを残す                                  | 境目が歴史的な偶然で説明できない                                                                          |
| 語彙を変える閾値を置く                                                       | ADR 0018 の却下した案と同じ                                                                               |

## 追補（2026-09-06）: コーパスの結果と検証する言語

M8 のコーパス（[research/readiness-vocabulary-corpus.md](../research/readiness-vocabulary-corpus.md)）で、Serena の 70 サーバーは全部 4 値に写り、新しい値は要らなかった。「疑問」の中身は信号の構造（複数トークンの並行、per-request / per-file の進捗、設定で無効な opt-in）と信号の不在で、時間でしか終わりを言えないのは Metals だけだった。

### 決定 F. 検証する言語は型ごとに 1 つ以上、数では削らない

決定 B-3 の出発点（Metals、Elixir、Kotlin、Nextflow）を、コーパスの型ごとに次の 11 に置き換える。削る理由になるのは「実物が取れず、近いもので測っても答えにならない」だけで、数は理由にしない。

| M   | 型                                     | サーバー                       | 入手                                                               | 確かめること                                                                           |
| --- | -------------------------------------- | ------------------------------ | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| M9  | 時間でしか終わりを言えない             | Metals                         | nixpkgs 1.6.8                                                      | トークン単位の `indexing` と `unknown` のどちらが正直か。時間なしで 7.2 が通るか       |
| M10 | ビルドが `didOpen` まで始まらない      | Elixir（expert）               | GitHub release v0.1.9 のバイナリ                                   | 開くまで `initializing` にとどめるか                                                   |
| M11 | 一次資料がない                         | Kotlin（JetBrains kotlin-lsp） | GitHub release v262.9593.0（fwcd 版では答えにならない）            | 実測で信号を取る                                                                       |
| M12 | per-request の同期                     | Nextflow                       | release の `language-server-all.jar`                               | 走査を誘発しないと `references` は正しいか。グローバルな readiness なしで 7.3 が通るか |
| M15 | 複数トークンの並行                     | haskell-language-server        | nixpkgs 2.13.0.0                                                   | 未完了トークン 0 で `ready` にして 7.2 が通るか                                        |
| M16 | 起動時の走査が無音                     | pyrefly                        | nixpkgs 1.3.0-dev.1                                                | 再チェックの進捗だけで `ready` を言えるか                                              |
| M17 | per-request / per-file の進捗          | crystalline                    | nixpkgs 0.18.0                                                     | 起動系と per-request 系のトークンを区別できるか                                        |
| M18 | opt-in の信号                          | sourcekit-lsp                  | nixpkgs 5.10.1                                                     | 観測者が `backgroundIndexing` を注入して `indexing` → `ready` を取れるか               |
| M19 | 信号の不在の曖昧さ                     | Gleam                          | nixpkgs 1.18.1                                                     | 依存ダウンロードがないときの `ready` を信号なしで言えるか                              |
| M20 | 進捗の機構をリクエスト処理にも使い回す | Haxe（haxe-language-server）   | vshaxe の VS Code 拡張（vsix）に同梱。単体の release も npm もない | 起動系のタイトルだけで `ready` を言えるか                                              |
| M13 | 相方サーバーとの合成（測定のみ）       | Vue                            | nixpkgs vue-language-server 3.3.10                                 | 接続ごとの保留で結果が完全になるか（決定 B-5）                                         |

省くもの: AL（VS Code 拡張の同梱で単体入手できない。実物が取れない）、Erlang（erlang_ls 自身の信号は "Indexing OTP / Applications / Dependencies" の 3 本の `$/progress` で明確に写り、疑問の中身は Serena の取り違え。語彙について確かめることがない）。

順序は M9 → M10 → M11 → M12 → M15 → M16 → M17 → M18 → M19 → M20 → M13（合成の測定は写像を書かないので最後）。各 M は決定 C の段階を踏む。写像を書けない結論（`unknown` が正直）も結果として記録する。

結果（2026-09-06、M9〜M12）:

- M9 Metals、M10 Expert: 済み（[research/metals-readiness-measurement.md](../research/metals-readiness-measurement.md)、[research/expert-readiness-measurement.md](../research/expert-readiness-measurement.md)）
- M11 Kotlin: **保留**。JetBrains kotlin-lsp の最新 release v262.9593.0 は起動時に "This build of intellij-server has expired" で終了し、新しい release がない。実物が動かないので次の release で測る。fwcd 版で代用しない（表のとおり答えにならない）
- M12 Nextflow: 済み（[research/nextflow-readiness-measurement.md](../research/nextflow-readiness-measurement.md)）。コーパスの「per-request の同期」は誤りで、`references` は同期しない。走査の完了を示す信号がなく、観測者が `workspaceFolders` を歩いて走査の集合を再現し、全部に `publishDiagnostics` が出たら `ready` とする。版が語彙に現れず（`serverInfo` なし）保証は宣言しない。設定を送らないクライアントには `initializing` のまま。観測者が設定を注入することはしない（決定 G の注入は信号の有効化であって、サーバーの初期化の肩代わりではない）
- M15 haskell-language-server: 済み（[research/haskell-language-server-readiness-measurement.md](../research/haskell-language-server-readiness-measurement.md)）。コーパスの「複数トークンの並行」は成り立たない。`$/progress` は lsp ライブラリが 1 秒より長いセッションにしか作らず（`optProgressStartDelay`）、kick や索引バッチごとに作り直されるのでほぼ出ず、出ても一部しか覆わない。索引中の `references` は増え続ける部分応答。`--test` で遅延を 0 にしても、バッチの隙間に不完全で、最後のトークンの後も索引が続く。readiness は `unknown`（仕様 8.2 の 3）、health は `source: "cradle"` の診断から。「時間で抑制された進捗は readiness の語彙ではない」が新しい型
- M16 pyrefly: 済み（[research/pyrefly-readiness-measurement.md](../research/pyrefly-readiness-measurement.md)）。コーパスのとおり起動時の索引は無音（stderr のログだけ）で、"Rechecking" は開いているファイルの型検査。索引の前は `[]`、途中は部分応答で、`lazy-blocking` でも残る。写像は書かず両軸 `unknown`。上流に「populate を `$/progress` に繋ぐ」を求める
- M17 crystalline: 済み（[research/crystalline-readiness-measurement.md](../research/crystalline-readiness-measurement.md)）。コーパスの「per-request / per-file の進捗」は成り立ち、疑問「起動系と per-request 系のトークンを区別できるか」の答えは「起動系のトークンはなく区別は要らない」。`$/progress`（token "workspace/compile/N"）は要求ごとのコンパイルで、要求はそれを同期で待ってから答えるので起動直後から完全。readiness は起動ログ "LSP server is ready." で `ready`（選ぶのは "[workspace] Found projects:"）。開いていないファイルのディスク上の変更は結果キャッシュのせいで織り込まれず監視もしない。health は `unknown`。版が語彙に現れないので保証は宣言しない
- M18 sourcekit-lsp: **保留**（[research/sourcekit-lsp-readiness-measurement.md](../research/sourcekit-lsp-readiness-measurement.md)）。`backgroundIndexing` は Swift 6.0 以降で、nixpkgs（固定 rev も nixos-unstable も）の sourcekit-lsp は 5.10.1。5.10.1 は索引をビルドからしか作らず、nixpkgs の Swift には `libIndexStore.so` がなく `references` は空のまま。実物（6.x）が nixpkgs に来たら測る。5.10.1 の `workspace/_pollIndex`（索引の同期を要求で扱う語彙）は記録した

### 決定 G. 観測者の規則 3 つは 8 章の範囲

コーパスで要ると分かった観測者の規則（複数トークンは未完了がなくなったら `ready`、per-request / per-file の進捗は readiness に写さない、opt-in の信号は観測者が有効化の設定や capability を注入してよい）は、いずれも観測者の合成の規則（仕様 8 章）の範囲で、サーバーの義務（3〜7 章）を変えない。仕様に書くかは M9〜M20 の実測を見てから決め、書くなら 8.2 に足す。
