# ADR 0021: 0.6.0 は nixd と nil を当て、ドッグフーディングを日常の環境に載せる

- 日付: 2026-09-08
- 状態: 採用
- 関連: [ADR 0020](0020-v0.5-dart-sorbet-jdtls-clangd.md)（0.5.0 の範囲と手順）、[ADR 0019](0019-v0.4-corpus-and-counterexamples.md) 決定 C（検証の段階）・G（観測者の注入）、[ADR 0018](0018-external-review-2026-09.md) 決定 C・D、[ADR 0016](0016-declaration-shape.md)（欠けを名指しする宣言の形）、[ADR 0009](0009-success-criterion-and-two-sided-reference.md) 決定 C-4（時間判定の排除）・D-5（保証は測った版に）、[research/readiness-vocabulary-corpus.md](../research/readiness-vocabulary-corpus.md)、[research/claude-code-dogfooding.md](../research/claude-code-dogfooding.md)

## 経緯

0.5.0（ADR 0020）で易しい 4 サーバーを当て、語彙も観測者の規則も動かなかった。CHANGELOG の予定は外向きの提出だったが、作者の日常の環境を調べると、ドッグフーディングが届いていない言語があった。

作者が日常的に書くのは Rust、Python、Nix である（`~/nix/nixfiles` と `~/github/*/flake.nix` を 2026-09-08 に調査）。Rust は 17 の flake のうち 14 が devShell に rust-analyzer を置き、うち rust-overlay の 13 は `1.97.1`（lsp-det の `TESTED_VERSIONS` は `1.98.0` と `2026-08-03`）。Python の LSP は VS Code の Pylance（中身は pyright）と ruff で、ruff の LSP（`ruff server`）は診断・整形・コードアクションだけで 7.0 の横断要求を持たない。Nix は nil と nixd の両方がシステムパッケージにあり、VS Code は nixd を使う。Claude Code で有効な LSP プラグインは rust-analyzer だけで、Python と Nix には何も付いていない。

つまり、Rust と Python は写像が既にあり、Nix だけが空白である。提出の前に Nix を当て、3 言語の観測を日常の環境に載せて仕様が動く可能性を潰し切ってから提出する方が、ADR 0018 決定 D（外部に出すまでは理想を追う）に合う。順序はユーザーの決定（Nix の実装 → ドッグフーディングの本番化 → 外向きの提出）。

## 決定

### A. 範囲

1. **0.6.0** は nixd と nil の 2 つに ADR 0019 決定 C の段階（`flake.nix` → 実測記録 → 写像を RED → GREEN → REFACTOR → 実サーバーの結合テスト → 保証の宣言）を当て、続けてドッグフーディングを作者の日常の環境に載せる。順序は nixd → nil → ドッグフーディング。写像を書けない結論（`unknown` が正直）も結果として記録する
2. 語彙と観測者の規則は動かさない前提で始める。動かす必要が出たら報告して止まり、ADR を書いてから既存の写像・準拠テスト・fork のパッチを追従させる。決定 E の問いは実測の後にユーザーが決める
3. 外向きの提出は 0.6.0 の後。2 サーバーで見つかった上流への提案は `docs/upstream-submissions.md` に行を足すだけにする
4. ruff の LSP は写像の対象にしない。コーパスに「横断要求なし、走査なし」の行を足すだけにする

### B. 入手

いずれも `flake.nix` の `servers` に足す。版の固定はそこ（ADR 0019 決定 D）。固定中の nixpkgs の版は作者のシステムと同じである。

| サーバー | 入手           | 版         | 実行時に要るもの                                                                                                       |
| -------- | -------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------- |
| nixd     | nixpkgs `nixd` | 2.9.2      | `<nixpkgs>`（`NIX_PATH`）。既定の式 `import <nixpkgs> { }` と NixOS のオプションの評価に使う。nix のバイナリは要らない |
| nil      | nixpkgs `nil`  | 2026-07-23 | `nix` のバイナリ（設定 `nix.binary`、既定 `nix`）。flake の入力と NixOS のオプションの評価に使う                       |

どちらも評価に nixpkgs の実体を要し、それは開発環境の側にある。実サーバーの結合テストは `#[ignore]` のローカル smoke で、CI には入れない（v0.1-design 6 章）。

### C. 各サーバーで確かめること

一次資料（`reference/nixd`、`reference/nil` の浅い clone。ADR 0018 決定 C）から見込んだ写像と、実測で確かめる疑問を先に書く。答えは追補に記す。

| サーバー | 名乗り                                                                                      | 見込みの写像                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | 確かめること                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| nixd     | `serverInfo` "nixd"、版あり（`LifeTime.cpp:162`）                                           | `initialize` の応答の後に `$/progress` が 2 本並行する（token は乱数。title "evaluating nixpkgs entries" と "evaluating nixos options"、end の message "evaluated …"。`LifeTime.cpp:60-81, 176-191`）。begin で `indexing`、未完了のトークンがなくなった end で `ready`。`workspace/configuration` の答えで式が変わると同じ対が再び走る（`Configuration.cpp:62-77`）。health は `window/showMessage` も `logMessage` も使わず `unknown`。worker の死は stderr にしか出ない                                                                               | 7.0 の要求のうち索引に依るのは nixpkgs の属性への `definition` だけ（`references` は同一文書内。`FindReferences.cpp:24-47`）。`definition` は worker への RPC をセマフォで待ち（`Definition.cpp:179-190`）、worker は 1 本の同期ループで評価を終えてから次を読む（`Connection.cpp:318`、`AttrSetProvider.cpp:278-293`）ので、サーバー自身が要求を待たせる型（Dart、jdtls）と見込む。実測で begin〜end の間の `definition` が完全か。`didChange` は主ループで同期に解析する（`Support.cpp:23-58`）ので `didChange` は織り込むと見込む。`didChangeWatchedFiles` は読まない                                                                                                                                           |
| nil      | `serverInfo` "nil"、版は `CFG_RELEASE`（nixpkgs のビルドで入るか実測。`server.rs:190-193`） | `initialized` の後、flake.nix / flake.lock の Created を自分に送って 100 ms の debounce の後に flake.lock を読み（`server.rs:196-236, 461-475`。この段には信号がない）、store にない入力があれば `window/showMessageRequest`（"Fetch"）を待ち、`nixpkgs` の入力があれば `$/progress`（token `nil/loadNixosOptionsProgress`）、設定 `autoEvalInputs`（既定 false）なら `nil/loadInputFlakeProgress`。begin で `indexing`、end で `ready`。失敗は `window/showMessage` type 1 で来る（"Failed to load flake workspace: …" ほか）ので health に写せる見込み | 7.0 の要求のうち flake の読み込みに依るのは `inputs.<name>` への `definition`（`goto_definition.rs:101-140`）で、依るのは progress のない段（flake.lock の読み込み）。要求は snapshot に対して答え待たない（`server.rs:930-939`）ので、`initialized` の直後の `definition` が空で、その窓に信号がないか。flake.lock に `nixpkgs` の入力がない workspace では begin が来ず `initializing` のままか（clangd の決定 (a) と同型）。`showMessageRequest` を答えないクライアント（Claude Code の挙動は未確認）で読み込みが止まるか。`didChange` は VFS を主ループで更新してから snapshot を取るので織り込むと見込む。flake.lock の `didChangeWatchedFiles` は動的登録（`server.rs:238-262`）で、再読み込みの対が再び走る |

### D. Nix の 2 サーバーは横断要求が単一文書に閉じる

nixd も nil も、`references` は要求のあった文書の中の使用箇所だけを返す（`FindReferences.cpp:24-47`、`references.rs:12-60`）。Nix の名前解決が文書ごとに閉じ、`import ./a.nix` を辿らないためで、索引の欠けではなく設計である。workspace の別のファイルからの参照は、開いていても返らない。

したがって 7.2 の 1（`ready` の後の `references` が事前に計算した完全な結果に一致する）は、ワークスペース全体の結果とは一致し得ない。仕様 5 章の `coverage.scope` は `"workspace"` と `"openDocuments"` の 2 値で、「要求のあった文書だけ」を名指しする値がない。

### E. `scope` の問いはユーザーが決める（実測の後）

決定 D の欠けをどう宣言するかは仕様の問いで、実装の都合で決めない（`CLAUDE.md` の絶対の制約）。案は 2 つ。

| 案                                                                    | 内容                                                                                                                                                         |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| (a) `coverage` を宣言しない                                           | readiness と health の通知だけ約束する（`notifications_only()`）。7.2 のテストは書かない。宣言は嘘にならないが、欠けが名指しされない                         |
| (b) 仕様 5 章の `scope` に `"document"`（要求のあった文書だけ）を足す | 欠けを名指しする宣言の形（ADR 0016）に沿う。仕様（英日）、`ServerStateProvider`、準拠テスト（7.2 の 1 を文書内の結果で検証）を改訂する。ユーザーの承認が要る |

実測（M25、M26）は問いの答えに依らないので先に進め、両サーバーの実測記録が揃った時点で問いを出す。それまで写像の `guarantees()` は (a) で書き、(b) が採られたら追従させる。

### F. ドッグフーディングの本番化

作者の日常の Claude Code に、Rust・Python・Nix の 3 言語で lsp-det を常に挟む。

1. `dogfood/claude-plugin/.lsp.json` に `.nix` の項目を足す。上流は nixd（作者の VS Code と同じ選択。Claude Code は拡張子ごとに 1 つのサーバーしか起動しない）。nil は準拠テストの対象だが日常の経路には載せない
2. rust-analyzer `1.97.1`（rust-overlay の版）を実サーバーの結合テストに通し、通れば `TESTED_VERSIONS` に足す。通らなければ理由を実測記録に書き、flake の側を上げる案をユーザーに出す
3. `~/nix/nixfiles` の側（Claude Code のプラグインの常時読み込み、`~/github/*` の devShell への lsp-det の追加）は lsp-det の外で、文面を作ってユーザーの確認をもらう。`dogfood/README.md` には「日常の環境に載せる」節を足し、手順を書く
4. 観測は第 7 回として `docs/research/claude-code-dogfooding.md` に追記する。項目は従来の 3 つ（起動と最初の横断要求のタイミング、タイムアウトとエラーの見せ方、未知の通知の扱い）に、Nix での `window/showMessageRequest` と `client/registerCapability` の扱いを足す

### G. マイルストーン

| M   | 内容                       | 段階                                                                                      |
| --- | -------------------------- | ----------------------------------------------------------------------------------------- |
| M25 | nixd                       | 決定 C の全段階。評価に観測できる時間を要する fixture（nixpkgs の実体を指す `NIX_PATH`）  |
| M26 | nil                        | 同上。flake.lock に `nixpkgs` の入力がある fixture と、ない fixture                       |
| M27 | ドッグフーディングの本番化 | 決定 F。M25 の後、M26 と並行してよい。決定 E の答えが出ていれば宣言を追従させてから載せる |

各 M は 1 つの PR。機械的な段階（写像・テスト・文書の反映）は実測記録を元に Sonnet に委ね、実測と設計、rebase と確認は Fable が行う（0.5.0 と同じ）。

### 却下した案

| 案                                                            | 却下理由                                                                                                                                           |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 先に外向きの提出を始める                                      | 日常の環境に載せて仕様が動く可能性を潰す前に出すと、提出の後に仕様を直すことになる。順序はユーザーの決定                                           |
| ruff の LSP に写像を書く                                      | 7.0 の横断要求を持たず、走査もない。写像で消せる嘘がない                                                                                           |
| Python は Pylance を測る                                      | 配布が VS Code の拡張に閉じ、単体で起動できない。中身は pyright で写像は既にある                                                                   |
| `scope: "openDocuments"` で宣言する                           | 開いている別の文書からの参照も返らないので、これも嘘になる（決定 D）                                                                               |
| `scope` の問いを実測の前に決める                              | 実測で `references` が別の文書に届く経路（`import` の追跡など）が見つかる可能性を残す。仕様の書き換えは実測とユーザーの承認の後（ADR 0020 と同じ） |
| nil の `autoEvalInputs` を `initializationOptions` に注入する | 信号の有効化ではなく評価の範囲を広げる設定で、観測者の注入の範囲（ADR 0019 決定 G）を超える。既定のまま測る                                        |
| 日常の経路に nil も載せる                                     | Claude Code は拡張子ごとに 1 サーバー。作者の VS Code の選択と揃えて nixd にする                                                                   |

## 追補（2026-09-08）: 結果

- M25 nixd: 済み（[research/nixd-readiness-measurement.md](../research/nixd-readiness-measurement.md)）。見込みの写像のとおり、title が "evaluating " で始まる `$/progress`（token は乱数の整数）の begin で未完了の集合に加えて `indexing`、end で外し、集合が空になった時点で `ready`。確かめること「begin〜end の間の `definition` が完全か」への答えは「完全」: controller が評価 worker への RPC をセマフォで待ち、worker は 1 本の同期ループで評価を終えてから次を読むので、サーバー自身が要求を待たせる型（Dart、jdtls）。先読みはしない。health は信号がなく常に `unknown`（失敗した評価の end も成功と同じ "evaluated …" で、死んだ worker への次の要求で nixd 自身が SIGPIPE で落ちる）。決定 D・E のとおり `references` は要求のあった文書に閉じ、`guarantees()` はどの版でも `notifications_only()`（決定 E の答えまで `coverage` を宣言しない）。実サーバーの結合テスト（2.9.2。`NIX_PATH` に nixpkgs が要る）で 7.1 の遷移と、評価中に送った `definition` が `ready` の後に nixpkgs の `hello/package.nix` を 1 件だけ指して返ることを確認した。7.1 の 3（`workspace/configuration` の答えの差し替えによる再評価）は準拠テストの汎用の応答機構を変えずには構成できず、実測（走行 6）の記録に留めた。上流への提案 3 件（失敗の end の区別、worker の死での SIGPIPE、`didChangeWatchedFiles` の黙殺）を `docs/upstream-submissions.md` に未着手で記した
