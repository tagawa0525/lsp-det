# ADR 0022: 仕様を安定版 1.0 にし、外向きの提出が指す版を固定する

- 日付: 2026-09-09
- 状態: 採用
- 関連: [ADR 0018](0018-external-review-2026-09.md)（決定 D。外部へのアクションの時期）、[ADR 0020](0020-v0.5-dart-sorbet-jdtls-clangd.md) と [ADR 0021](0021-v0.6-nixd-nil-and-daily-dogfooding.md) の追補（2026-09-09。`unknown`）

## 経緯

外向きの提出（`docs/upstream-submissions.md`）は「上流に通した後で仕様を変えたくなれば相手に迷惑」を理由に 0.5.0 の後まで止め、外部に出すまでは理想を追ってきた（ADR 0018 決定 D）。戦略への批判的レビュー（[research/upstream-strategy-review-2026-09.md](../research/upstream-strategy-review-2026-09.md)）は、仕様が `Status: draft` のままでは「安定してから来い」で止まること、LSP 本体で最初に来る反論「乱立の多くはサーバー自身が要求を待たせる形で解決済みで通知は不要」への答えが文書にないことを指摘した。nil と clangd の `unknown`（ADR 0020、0021 の追補 2026-09-09）で 8.1 の `readiness: "unknown"` の定義も実態と合わなくなった。

## 決定

### A. 仕様に固有の版を持たせ、1.0 を lsp-det v0.7.0 で凍結する

- 冒頭の `Status` を `stable` にし、仕様の版 1.0 と凍結した lsp-det の tag（v0.7.0）を書く。上流に出す文書は proxy ではなく仕様を指すので、版は仕様に固有のものにし、tag は「どのコミットか」の補助にする
- 以後の変更は版を上げ、11 章「変更記録」に記す。提出の後に仕様を変えるなら、出したものには変更点を追記する（`docs/upstream-submissions.md` の規則）

### B. 6 章 4 項に「サーバー側の保留との関係」を足す

索引が終わるまで 7.0 の要求をサーバー自身が待たせる方式（Dart、jdtls、gopls、nixd）は、索引未完了の空応答は消すが、壊れたサーバーの成功風応答と編集を織り込まない応答は消さず、判断をクライアントから奪う。保留は `health` と `freshness` を言えず、部分的な答えで先に進みたいクライアントに進ませず、クライアントからは無応答のサーバーと区別がつかない。本プロトコルは状態を見えるようにして待つかどうかをクライアントの判断にし、サーバーが保留することは禁じない。保留しつつ話すサーバーは保留中 `indexing` を報告する。置き場所は「代わりにならない仕組み」を列挙する 6 章 4 項。

### C. 8.1 の `readiness: "unknown"` を「信号が来ないと観測者が判断した」まで広げる

観測する手段がない場合に加え、この workspace では信号が来ないと観測者が判断した場合（`nixpkgs` の入力のない nil、compilation database のない clangd）を含める。`unknown` から後に begin が来て `indexing` になることは、この定義と矛盾しない。

### D. 0.7.0 として release する

nil と clangd の挙動変更（`unknown`）と仕様の安定版化を合わせて 0.7.0 の tag を打つ。提出物が指す tag が要る。

### 却下した案

| 案                                               | 却下理由                                                                                                         |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `Status: draft` のまま提出する                   | 「安定してから来い」で止まる（レビューの指摘 5 (e)）                                                             |
| 版を持たせず lsp-det の tag だけで指す           | 上流に出す文書は仕様を指す。proxy の版が上がるたびに仕様が変わったように見える                                   |
| 保留との関係を 1 章（目的）や 9 章の前書きに置く | 6 章 4 項が「代わりにならない仕組み」の列挙で、その続きが最も自然                                                |
| 保留を禁じる                                     | Dart、jdtls のようにサーバーが待たせることは害ではない。見えないことが害。本プロトコルは情報を伝えるだけ（1 章） |

## 影響
