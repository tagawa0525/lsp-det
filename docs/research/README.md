# Research notes

These are records of measurement and investigation. Following `CLAUDE.md`'s reading
order, read them after the spec and the design doc. Most are in Japanese; only
`claude-code-dogfooding.md` also has an English version. They follow the policy of
confirming a server's own signals from its documentation and real measurement before
writing a mapping (ADR 0018 decision C).

## Readiness measurements of individual servers

| Document                                                                                                   | Language | What it establishes                                                                                                                                                                                                                                       |
| ---------------------------------------------------------------------------------------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [clangd-readiness-measurement.md](clangd-readiness-measurement.md)                                         | Japanese | clangd emits `$/progress` (token `backgroundIndexProgress`) for background indexing when the client declares `window.workDoneProgress`, and `references` is a growing partial response during indexing, correcting spec chapter 10 (2026-09-06).          |
| [crystalline-readiness-measurement.md](crystalline-readiness-measurement.md)                               | Japanese | crystalline has no startup-phase progress token; `$/progress` covers only per-request compilation that requests already wait for synchronously, so readiness maps from the post-`initialized` log message alone (2026-09-06).                             |
| [dart-and-sorbet-readiness-vocabulary.md](dart-and-sorbet-readiness-vocabulary.md)                         | Japanese | Confirms from primary sources that both Dart analysis server and Sorbet expose a quiescent-style readiness notification, matching rust-analyzer's `quiescent`, though their guarantees remained unmeasured (2026-09-04).                                  |
| [dart-readiness-measurement.md](dart-readiness-measurement.md)                                             | Japanese | Measured against 401 files, Dart analysis server itself holds requests until analysis completes, so `references` is always complete after startup or edits, mapped from the `ANALYZING` progress token (2026-09-06).                                      |
| [expert-readiness-measurement.md](expert-readiness-measurement.md)                                         | Japanese | Expert (Elixir) starts its build engine on `initialized` rather than `didOpen`, so readiness maps without time, but `didChangeWatchedFiles` never triggers reindexing, leaving `freshness.fileChanges` empty (2026-09-06).                                |
| [gleam-readiness-measurement.md](gleam-readiness-measurement.md)                                           | Japanese | Gleam's dependency-download `$/progress` token always begins and ends right after `initialized`, even with nothing to download, so readiness never needs a fallback wait; a `gleam.toml` change can leave `references` empty (2026-09-06).                |
| [gopls-readiness-measurement.md](gopls-readiness-measurement.md)                                           | Japanese | Measured against real gopls, the `$/progress` mapping from the design (title "Setting up workspace" begin/end) matches source reading and correctly yields `initializing` to `indexing` to `ready` (2026-09-03).                                          |
| [haskell-language-server-readiness-measurement.md](haskell-language-server-readiness-measurement.md)       | Japanese | haskell-language-server's "Indexing"/"Processing" progress tokens are not a readiness vocabulary: a 1-second start delay and per-batch token churn leave `references` returning growing partial results, so the honest mapping is `unknown` (2026-09-06). |
| [haxe-language-server-readiness-measurement.md](haxe-language-server-readiness-measurement.md)             | Japanese | haxe-language-server's `$/progress` titles distinguish three fixed startup operations from three fixed request operations, so readiness maps from titles alone while requests block on the compiler until complete (2026-09-06).                          |
| [jdtls-readiness-measurement.md](jdtls-readiness-measurement.md)                                           | Japanese | Measured against 201 classes, jdtls holds requests until its own indexing completes, so `references` after `ServiceReady` (`language/status`) is always complete, and health maps from `ProjectStatus` and project diagnostics (2026-09-06).              |
| [metals-readiness-measurement.md](metals-readiness-measurement.md)                                         | Japanese | Metals can be mapped without time: readiness should wait until the first "Indexing" progress token ends, and reindexing should be predicted from build-file and source-change notifications, refuting the corpus's time-only assessment (2026-09-06).     |
| [nextflow-readiness-measurement.md](nextflow-readiness-measurement.md)                                     | Japanese | Nextflow's `references` never synchronizes; the only completion signal is `publishDiagnostics` reaching every workspace file, so an observer that reproduces the file set can map readiness without time (2026-09-06).                                    |
| [nil-readiness-measurement.md](nil-readiness-measurement.md)                                               | Japanese | nil gives no signal while reading `flake.lock` (about 100ms), after which an evaluation-progress begin is the first signal; workspaces without a `nixpkgs` input start from `unknown` rather than staying `initializing` (2026-09-08).                    |
| [nixd-readiness-measurement.md](nixd-readiness-measurement.md)                                             | Japanese | nixd runs two parallel `$/progress` tracks (title "evaluating …") for nixpkgs and NixOS-option evaluation and itself holds index-dependent requests until evaluation completes, but it emits no health signal (2026-09-08).                               |
| [pyrefly-readiness-measurement.md](pyrefly-readiness-measurement.md)                                       | Japanese | pyrefly's startup indexing produces no protocol signal at all, and `references` moves from empty to partial to complete with nothing to distinguish the phases, so both axes are honestly `unknown` (2026-09-06).                                         |
| [pyright-readiness-measurement.md](pyright-readiness-measurement.md)                                       | Japanese | Measured pyright behavior diverged from ADR 0010's assumptions on two points, missing `serverInfo` and a source-enumeration completion log, leading ADR 0011 to redefine the mapping-selection method and readiness signal (2026-09-03).                  |
| [rust-analyzer-quiescent-measurement.md](rust-analyzer-quiescent-measurement.md)                           | Japanese | Measured against real rust-analyzer, disk writes and in-memory `didOpen`/`didChange` do not flip `quiescent`, but a `Cargo.toml` change does, flipping it back to `true` after about 0.25 seconds (2026-08-29).                                           |
| [sorbet-readiness-measurement.md](sorbet-readiness-measurement.md)                                         | Japanese | Measured against 601- and 3001-file fixtures, Sorbet holds cross-file requests whenever it is not Idle, mapping operation starts to `indexing` and the point where none remain to `ready` (2026-09-06).                                                   |
| [sourcekit-lsp-readiness-measurement.md](sourcekit-lsp-readiness-measurement.md)                           | Japanese | The opt-in background-indexing signal cannot be measured on nixpkgs's sourcekit-lsp 5.10.1 (pre-6.0, and missing `libIndexStore.so`), so this milestone is deferred until a newer build is available (2026-09-06).                                        |
| [typescript-language-server-readiness-measurement.md](typescript-language-server-readiness-measurement.md) | Japanese | Confirms the "Initializing JS/TS language features…" progress mapping from source reading, and finds a SIGKILLed tsserver leaves the language server alive, returning an empty array as a successful response (2026-09-03).                               |
| [vue-composition-measurement.md](vue-composition-measurement.md)                                           | Japanese | With Vue's Hybrid Mode, cross-file answers for `.vue` files come entirely through the typescript-language-server connection, so per-connection holding suffices and lsp-det need not know about the sibling connection (2026-09-06).                      |

## Cross-server surveys

| [proxy-implementations.md](proxy-implementations.md)             | Japanese | Reads ra-multiplex, emacs-lsp-booster, and lsp-devtools and finds their framing spans full-parse, one-directional-parse, and no-parse designs, recommending lsp-det parse only headers and peek `method`/`id` while passing the body verbatim.                      |
| [readiness-vocabulary-corpus.md](readiness-vocabulary-corpus.md) | Japanese | Maps Serena's 70 supported language servers to lsp-det's readiness vocabulary from each server's own documentation and source, producing the list of servers whose mapping is in question and candidates for real-server measurement (2026-09-06).                  |
| [server-readiness.md](server-readiness.md)                       | Japanese | Reads pyright, typescript-language-server, and eclipse.jdt.ls source to find how each exposes readiness: work-done progress tied precisely to file counts for pyright, and a tsserver project-load progress that also ends on crash for typescript-language-server. |
| [vscode-languageclient.md](vscode-languageclient.md)             | Japanese | Reading vscode-languageserver-node finds that jsonrpc's `sendRequest` never times out; the only time-based handling is a 2-second shutdown wait and a 10-second stalled-byte-stream warning (2026-08-27).                                                           |
| [zed-lsp.md](zed-lsp.md)                                         | Japanese | Zed subscribes to rust-analyzer's `experimental/serverStatus` but deserializes only `health` and `message`, never reading the `quiescent` field, which does not appear anywhere in Zed's codebase (2026-08).                                                        |

| [lsp-pain-points-synthesis.md](lsp-pain-points-synthesis.md)       | Japanese | Integrates the three pain-point surveys into a scored map (evidence strength, frequency, severity, proxy feasibility, upstream prospects) and re-derives extension candidates from scratch instead of the earlier fixed three-extension framing.                                |

## Serena

| [serena-solidlsp.md](serena-solidlsp.md)                               | Japanese | Reads solidlsp's per-language readiness handling and finds six patterns (server-specific notifications, progress-token draining, log-message matching, first diagnostics, fixed sleeps, immediate-ready), all falling back to proceeding anyway after a timeout. |
