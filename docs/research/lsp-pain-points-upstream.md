# LSP 本体への不満・限界の棚卸し(upstream issue トラッカー調査)

調査日: 2026-08-28
対象: microsoft/language-server-protocol の GitHub issue トラッカー
(調査時点で open 277 件 / closed 942 件)

## 要約

- LSP 本体トラッカーの不満の大半は「機能追加要望」(open issue の 7 割超が
  `feature-request` ラベル)であり、決定性・機械可読性そのものを正面から
  扱う issue は少数派である。しかしその少数派は 2016〜2018 年起票のまま
  未解決で残り続けており、質的には最古参・最長寿の課題群である。
- lsp-det の 3 拡張はいずれも upstream で長期未解決の課題に直接対応する。
  B(準備完了の不在)は #511(2018 年起票、今も open)と #1367(push 型
  readiness 通知が `ServerCancelled` を理由に閉じられた)、C(起動の仕様外)
  は #2051・#2127・#227 など、A(シンボル範囲の実装依存)は #327 の議論で
  「range は AST ノード範囲を表すとは限らない」と明言されたまま仕様化
  されていない点に根拠がある。
- 決定性に関わるが lsp-det の 3 点に含まれない課題として、position
  encoding(#376、リアクション数で歴代最多の 145)、部分結果の意味論
  (#1336)、`isIncomplete` の意味論(#954)、診断の null 応答(#1882)、
  診断の完了通知(#54・#737)などが存在する。#376 は 3.17 の
  `positionEncoding` で解決済みであり、「決定性の欠陥は放置されるとは
  限らないが、解決までに 4 年以上を要する」ことを示す前例でもある。

## 調査方法

GitHub の公開 Search API / Issues API(認証なし)を使用した。

```text
GET https://api.github.com/search/issues
    ?q=repo:microsoft/language-server-protocol is:issue is:open
    &sort=reactions-+1&order=desc
GET https://api.github.com/repos/microsoft/language-server-protocol/issues
    ?state=open&per_page=100&page=N
```

- リアクション(+1)順の open issue 上位を取得
- open issue 全 277 件を取得しラベル・起票年の分布を集計
- キーワード検索(documentSymbol range / readiness / indexing /
  diagnostics finished / position encoding / partial result / startup 等)
  で closed を含む関連 issue を横断取得
- 主要 issue は本文・コメントを個別取得して要旨を確認

## 分類別の傾向

### (a) 決定性・機械可読性の問題

件数は少ないが長寿命。仕様の曖昧さ(clarification)として起票されるか、
「クライアントごとに挙動が違う」という形で顕在化する。代表例:

- #511 / #1367: readiness の標準が無い(後述)
- #1882: 診断応答の null 許容が仕様と実装(VS Code)で乖離
- #1336: `PartialResult` の要件(後続部分が前の結果を無効化できるか)が未定義
- #954: `isIncomplete=false` の正確な意味論が未定義
- #972: `workspace/configuration` の設計がクライアント側で実装不可能
- #648: 補完アイテムの入力テキスト(filterText/textEdit)の解釈が曖昧
- #2216: 不正な glob パターンの扱いが未定義
- #2060: ドキュメント変更後の `completionItem/resolve` の有効性が未定義
- #2053: `didChange` のバージョン番号がオーバーフローした場合の挙動が未定義

### (b) 機能追加要望

最大勢力(feature-request 200 件)。リファクタリング(#1164・#61)、
補完の拡張(30 件)、references の拡張(#1911・#396)、リモート FS
(#1264)など。lsp-det の関心とは概ね独立。

### (c) エディタ UI 都合

ユーザー対話(#1164・#1641)、Code Action のグループ表示(#994)、
ステータス表示など。VS Code の UI モデルが仕様に浸透していることへの
不満も散見される(#972 のコメント等)。

### (d) プロセス・ガバナンス

- #1642: サーバー/クライアント実装者のコミュニティスペース再考
- #2220: 公式メタモデル実装 lsprotocol のメンテナンス状況への懸念
- #512: BSP など隣接プロトコルとの関係
- #2127: エディタ非依存のサーバー設定ファイル(ガバナンスと C の中間)

## lsp-det の 3 拡張との対応

### A: シンボル範囲の実装依存

直接の裏付けは closed issue #327(2017)にある。当時の仕様の説明として
「location の range は AST ノードの範囲を表すとは限らない」
「`containerName` から階層を再構成することはできない」と明言され、
3.10 で `DocumentSymbol`(階層+`range`/`selectionRange`)が導入された。
しかし `range` が何を含むか(doc コメント、属性、修飾子等)は今も
実装依存のままで、以下が残存する。

- #1255(open, 2021): `DocumentSymbol` が同一ファイル内の Range しか
  表現できない(複数ファイルにまたがるシンボルを表せない)
- #98(open, 2016): 可視性などシンボル属性の表現力不足
- #2140(open, 2025): 可視性 SymbolTag の追加要望(#98 の再演)
- #884(closed): `SymbolInformation` と `DocumentSymbol` の二重定義の混乱
- #2118(open, 2025): 言語固有詳細を構造化して返す提案

upstream は「シンボルの範囲がどの構文要素を含むか」を規定する動きを
見せておらず、範囲の決定性はクライアント・サーバー間の暗黙の合意に
委ねられ続けている。

### B: 準備完了(readiness)の不在

最も証拠が厚い領域。

- #511(open, 2018〜): readiness インジケータの標準化を求める議論。
  コメント欄に実害の証言が集中している:
  - YouCompleteMe 開発者:「jdt.ls のメッセージを独自パースして
    『実際にリクエストに応答できる時点』を推測している。自動テストでは
    さらに悪化する。真の ready リクエスト/通知があればサーバー固有
    コードは不要になる」(2020-07)
  - rust-analyzer 開発者(matklad): 標準が無いため独自拡張
    `experimental/serverStatus` を策定(2021-04)
  - erlang_ls: 当初は索引完了まで `initialize` 応答を遅延させ、UX 悪化の
    ため `workDoneProgress` に移行したが根本解決になっていない
- #1367(closed, 2021): サーバーが処理完了時に `idle` 通知を送る提案。
  メンテナは `ServerCancelled`(busy なら再送を依頼するエラーコード)で
  解決済みとして 5 日で close。起票者は「クライアントは尋ねるまで busy か
  分からず、デバウンス短縮に使えない」と反論しており、push 型 readiness の
  不在は意図的な設計判断として固定されている
- #54(closed, 2016→2019): 索引ワークフロー(再索引の指示、進捗、
  完了通知)の仕様化要求。3.15 の `workDoneProgress` 導入で close されたが、
  progress は人間向け表示であり「完了したら結果が安定している」ことを
  機械が判定する契約ではない
- #646(open, 2018): サーバーが不整合状態からの再起動を要求できない
- #227(open, 2017): 接続状態遷移が仕様外でクライアント実装頼み
- #1572(open, 2022): `ServerCancelled` を返せるリクエストが限定的

要するに upstream の公式回答は「progress(人間向け)+ `ServerCancelled`
(ポーリング)で足りる」であり、決定的な readiness 契約(この時点以降の
応答は安定しているという保証)は 8 年間提供されていない。

### C: 起動の仕様外

仕様は「サーバーをどう起動・発見・設定するか」を明示的にスコープ外と
しており、それへの不満が繰り返し起票されている。

- #2051(open, 2024): Jupyter カーネル方式のサーバー自動発見
  (`~/.lsp` に起動コマンドと対象ファイルパターンを登録)の提案
- #2127(open, 2025): エディタ非依存の設定ファイル(`.lsp.toml`)提案。
  現状は `.vscode` `.helix` `.zed` がリポジトリに乱立
- #1640(open, 2023): サーバー設定フォーマットの JSON Schema 公開
- #227(open, 2017): 起動・クラッシュ・リトライの手順が仕様外
- #674(open, 2019): サーバーとプロジェクトの対応関係(1 サーバー n
  ワークスペース可否)を宣言できない
- #558(open, 2018): PID・ログ位置等を返す ServerInfo リクエストが無い
- #335(open, 2017): クライアント対応 URI スキームの宣言手段が無い
- #642(open, 2018): コマンドの利用可否をサーバーが知る手段が無い

いずれも「プロトコル本体の外側」とされ、10 年近く放置されている。
サーバー起動の再現性(同一コマンド・同一環境で同一挙動)を保証する
仕組みは upstream に存在しない。

### 3 点に含まれないが決定性に関わる課題

lsp-det のスコープ外だが、決定性の観点で認識しておくべきもの。

| # | 状態 | 要旨 | lsp-det との関係 |
| --- | --- | --- | --- |
| #376 | closed | 位置の単位が UTF-16 固定(+1 = 145、歴代最多)。3.17 の `positionEncoding` で解決 | 位置の決定性。解決に 4 年超を要した前例 |
| #872 | open | LSIF の既定エンコーディングを非 UTF-16 に | 同上の残務 |
| #737 | closed | 診断の明示的リクエスト(pull 型)。3.17 の `textDocument/diagnostic` で解決 | 診断タイミングの決定性の部分的解決 |
| #1882 | open | 診断 null 応答の許容が仕様と実装で乖離 | 応答の機械可読性 |
| #256 | open | ファイル非依存(プロジェクト全体)診断が表現不可 | 診断の完全性 |
| #510 | open | 逐次型診断とビルド時診断の区別が無い | 診断の意味論 |
| #1336 | open | 部分結果が前の結果を無効化できるか未定義 | 結果の安定性 |

| #558 | open | ServerInfo(health 情報)の欠如 | 可観測性 |

## 結論

1. upstream の不満の量的中心は機能追加要望であり、lsp-det が扱う
   決定性の欠陥は「声の大きい」課題ではない。ただしライフサイクル・
   readiness・仕様の曖昧さに関する issue は 2016〜2019 年から未解決の
   まま残る最長寿群であり、upstream が構造的に解決しない(スコープ外と
   宣言している、または `ServerCancelled` 等の部分的回答で閉じている)
   領域である。拡張プロトコルとして外側から解決する lsp-det の設計判断は
   この構造と整合する。
2. 3 拡張の各々に対応する一次証拠: A は #327(range は AST ノードとは
   限らないという明言)と #1255・#98 の残存、B は #511 のテスト自動化の
   証言と #1367 の close 理由、C は #2051・#2127・#227 の長期放置。
3. #376(position encoding)の顛末は、決定性の欠陥が最終的に仕様に
   取り込まれ得ること、ただし合意まで数年を要することを示す。lsp-det の
   拡張が将来 upstream 化される場合の参照事例となる。
