### typescript-language-server: `fix: answer requests with RequestFailed when tsserver is not running`

PR 先: `typescript-language-server/typescript-language-server`（master）。ブランチ: `tagawa0525/typescript-language-server` の `no-server-request-failed`（1 コミット、`src/ts-client.ts` と `src/ts-client.test.ts`）。

本文:

```markdown
When tsserver has exited (crashed, or was killed by the OS) the language server keeps running and answers every later request with `ServerResponse.NoServer`, which the request handlers turn into an empty success: `textDocument/references` returns `[]`, `definition` returns `null`, hover returns nothing. A client cannot tell that from a real answer, and a coding agent that asks "who references this symbol?" before a rename or a deletion reads `[]` as "nobody".

How to reproduce: open a file, `kill -9` the tsserver child process, then send `textDocument/references`. The server logs `[tsserver] Exited. Code: null. Signal: SIGKILL` and answers the request with `{"result": []}`.

This change makes `TsClient.execute` and `executeCustom` reject with an LSP error response when there is no running tsserver: `LSPErrorCodes.RequestFailed` (-32803) with the reason in the message (`tsserver exited (code: null, signal: SIGKILL); cannot execute references`, the error of a failed start, or `tsserver is not running` after shutdown). The request handlers need no change: the rejection propagates as an error response through `vscode-languageserver`. Fire-and-forget requests (`executeWithoutWaitingForResponse`) and the diagnostics path (`executeAsync`, which only observes completion) are unchanged, so nothing new is rejected on a notification path.

Restarting tsserver after a crash would be the next step; this change only stops presenting a dead server as a working one.

Tests: two cases in `ts-client.test.ts` (tsserver killed underneath the client; after `shutdown()`). `vitest run` and `lint` pass.
```
