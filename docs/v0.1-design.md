# lsp-det v0.1 Design

[日本語](v0.1-design.ja.md)

> A reference implementation of the server state protocol ([spec/server-state.md](spec/server-state.md)). A transparent proxy that sits between the client and the language server, where the upstream side stands in for the language server and the downstream side stands in for the client. It places the LSP boundary at lsp-det's center, and above that boundary a protocol-conformant exchange always flows. The upstream side maps upstream's vocabulary onto the protocol, and the downstream side behaves as a client that uses the protocol correctly. Both sides are reference implementations that show what is missing from the language server itself and the client itself.
>
> For the long-term vision (specifying the three extensions, including declaration range and the launch manifest), see [vision.md](vision.md); for the grounds of the success criterion and the structure, see [adr/0009](adr/0009-success-criterion-and-two-sided-reference.md) (Japanese). This document defines v0.1's implementation scope.

## 1. Purpose and Success Criteria

- **Purpose**: Fill the "server state" vocabulary LSP lacks. The spec (`docs/spec/`) is the primary deliverable, and the implementation demonstrates it (ADR 0003 decision 7, ADR 0006 decision 1)
- **Success criterion**: The server state protocol's spec, the conformance tests for the upstream side and the downstream side, and the reference implementations of the upstream side and the downstream side are self-consistent and pass when applied to rust-analyzer and gopls. No time condition is set. A native implementation in a real server, client adoption, and a proposal to LSP itself are ordered next stages (ADR 0009 decision A)
- **Means of observation**: Run it in the author's Claude Code environment to catch real-server behavior the conformance tests miss. Running it is not itself the success criterion. Observations are recorded under `research` and used as grounds for spec chapter 10. The Serena path comes after v0.1 (chapter 9)
- **Team**: One person, 20 hours a week

### The Underlying Problem

1. The client sends `textDocument/references` and the like right after `initialize` completes
2. The server returns an empty array `[]` because indexing is not complete (legal under LSP)
3. The agent misreads it as "no references" and breaks something with a deletion, a rename, and so on

LSP has no standard for "readiness". Only rust-analyzer (`experimental/serverStatus`) and jdtls (`language/status`) have a machine-readable notification, and even those two differ in format (details in [vision.md](vision.md), 6.2).

## 2. Scope

### In Scope

- A **transparent proxy** for a single client and a single upstream (a single Rust binary, no external runtime dependency)
- **The upstream side** (→ 4.2): Maps the language server's vocabulary onto the server state protocol. Provides the `experimental/serverState` request, the `experimental/serverStateChanged` notification, and a capability declaration with guarantees, on upstream's behalf. Two mappings (adapters): **rust-analyzer** and **gopls**
- **The downstream side** (→ 4.3): A reference implementation of spec chapter 9, "Recommended client behavior". On behalf of a client that does not speak the protocol, it holds cross-workspace requests until `ready` (a gate)
- **The conformance test suite** (→ chapter 6): The set of tests that makes spec chapters 7 (server), 8.4 (observer), and 9.1 (client) executable. The upstream side is the subject of spec chapter 7 and 8.4, and the downstream side is the subject of 9.1. Swapping the subject applies the same suite to real servers and real clients
- Running as a Claude Code plugin (`.lsp.json`) (a means of observation)

### Out of Scope (Explicit Non-Goals)

- Multiplexing (sharing across multiple clients). Entirely avoids ra-multiplex's hard spots (ID rewriting, capability merging)
- Synthesizing declaration range (vision.md chapter 1, frozen). No parser (tree-sitter and the like) is bundled
- A config file, a manifest, a registry, an installer
- Incidental features like a dashboard, an unbounded cache
- **Time-based judgment**. Neither a cutoff timer for holds nor synthesizing "treat it as `ready` after some time" (spec chapter 6, item 6; ADR 0009 decision D-10). Detecting a hang is the responsibility of the real client's own timeout, outside this proxy

## 3. Launch Interface

Complete through argv. The proxy has no config file and no flags of its own.

```text
lsp-det -- <upstream command> [args...]
```

- Runs everything after `--` as-is as the upstream command (the language server's own launch command line)
- Which mapping to use is decided by the name upstream gives in `InitializeResult.serverInfo.name` (4.2). A server that does not return `serverInfo` (pyright) is decided by the name it gives itself in a `window/logMessage` it sends at startup (ADR 0011). The command name is not looked at (it does not match when launched through a wrapper script)
- The launch specification lives permanently in the caller's config file (CC's `.lsp.json`, Serena's `ls_args`). This is what guarantees reproducibility; launching by hand from a shell is not an assumed operation
- If a flag becomes necessary in the future and it no longer fits on one line, `--config <explicit path>` is added later. **No implicit file search is introduced**

An example CC plugin `.lsp.json` (the real one is in `dogfood/claude-plugin/`; launch with `claude --plugin-dir dogfood/claude-plugin`; the procedure is `dogfood/README.md`):

```json
{
  "rust": {
    "command": "lsp-det",
    "args": ["--", "rust-analyzer"],
    "extensionToLanguage": { ".rs": "rust" }
  }
}
```

## 4. Behavior Specification

### 4.1 Structure: Both Sides Always Run

```text
client ──[plain LSP]── downstream side ──[LSP + server state protocol]── upstream side ──[plain LSP]── language server
                        (stands in for       the boundary inside lsp-det       (maps the
                         the client)                                            server's vocabulary)
```

- lsp-det always runs both the upstream side and the downstream side. It has no flag to switch between them
- The upstream side becomes the identity mapping when upstream declares the protocol itself (adds no declaration, passes requests and notifications through as-is). If not declared, a mapping supplements upstream's vocabulary and declares on upstream's behalf
- The downstream side, when the downstream (client) declares `experimental.serverState`, just forwards the state across the boundary and does not wait (spec 5.2). If not declared, it stands in for the recommended behavior of spec chapter 9
- There is no override flag. A client that declares the capability but does not wait is a case where the reference implementation shows what that client lacks — not something for lsp-det to hide (ADR 0009 decision D-7)

### 4.2 The Upstream Side (Standing in for the Language Server)

- **Injecting capabilities**: The capability a mapping needs is **added** to the client's `ClientCapabilities` in the `initialize` sent to upstream, and forwarded (everything else unchanged). Since `serverInfo` is known only from the `initialize` response, capabilities for every known mapping are injected **unconditionally**. Both are nothing more than "permission to send the notification"
  - `window.workDoneProgress: true` (needed for gopls's progress notification; without it, it falls back to `window/showMessage`)
  - `experimental.serverStatusNotification: true` (rust-analyzer; without it, `experimental/serverStatus` is never sent at all)
  - `experimental.serverState: true` (the subscription declaration for this protocol. Needed so the downstream side can read the notification when upstream speaks this protocol itself. A notification that arrives is not passed on to the client unless the client declared it)
- **Selecting the mapping**: Chosen by upstream's `InitializeResult.serverInfo.name` (`"rust-analyzer"` / `"gopls"` / `"basedpyright"`; all confirmed from source and measurement). Without `serverInfo`, chosen by the name upstream gives itself at startup in `window/logMessage` (the pyright family's "Pyright language server 1.1.412 starting"). This choice may happen before the `initialize` response arrives, and if `serverInfo` comes afterward, it is reselected from that (ADR 0011 decision A). Matching names is case-insensitive (`serverInfo.name` is a free-form display string, and pyright's productName is "Pyright"). When a name pointing to the same mapping arrives later, the mapping and the observation are kept, and the mapping decides how to update the version it uses as grounds for a guarantee (`Mapping::learn_identity`; for pyright, `serverInfo`'s version is the product's version as-is; for typescript-language-server, `serverInfo`'s version is the wrapper's version, and the TypeScript version the guarantee depends on is taken from the startup log and `$/typescriptVersion`). Without a name, or with an unknown name, there is no mapping and both axes are `unknown` (spec 8.2 item 3)
- **The identity mapping**: If upstream's `InitializeResult` has `serverStateProvider`, no declaration is added, `experimental/serverState` is forwarded to upstream, and no notification of its own is sent (spec 8.2 item 6). In this case, the state above the boundary is read from upstream. Since upstream's notification arrives only on a change, lsp-det itself gets the initial state by querying upstream's `experimental/serverState` (the id is the string `"lsp-det:serverState"`, which never collides with the integer client ids; the response is not shown to the client). Until the response arrives, the downstream side waits as `initializing`, corresponding to "right after `initialize`"
- **Declaration**: Returns a per-mapping guarantee declared in `InitializeResult.capabilities.experimental.serverStateProvider`. Upstream's capability is not replaced; the declaration is only **added**
  - rust-analyzer: `{coverage: true, freshness: true}` (confirmed by running conformance tests 7.2 / 7.3 against a real rust-analyzer; rustup's 1.98.0 and nixpkgs's 2026-08-03)
  - gopls: `{coverage: true, freshness: true}` (confirmed with v0.23.0; 5.2)
  - No mapping: `true` (no guarantee)
- **Tested versions**: A guarantee is declared only for "a version of the language server that has passed the conformance tests" (spec 8.2 item 5). A mapping holds that list (`TESTED_VERSIONS`), and falls back to `true` when the version `serverInfo.version` gives is not in the list. It is not a semver range because even the same rust-analyzer gives itself as `1.98.0 (…)` for the rustup distribution and `2026-08-03` for the nixpkgs build, and the formats do not line up. lsp-det cannot vouch for upstream's internals and has only the observation that it passed the tests. The development environment is pinned by `flake.nix`, and when `flake.lock` is updated and a version changes, the list is moved only after the real-server integration tests pass
- **State**: Answers `experimental/serverState` immediately with the `ServerState` at the moment of the query, and sends `experimental/serverStateChanged` whenever `health` or `readiness` changes (only when downstream declared it). Until the first signal arrives, `health` is `unknown` and `readiness` is `initializing`, corresponding to "right after `initialize`" (spec 8.2 item 2)
- **Passing legacy notifications through**: rust-analyzer's `experimental/serverStatus` and the like flow through to downstream verbatim (ADR 0006 decision 4)
- **A request originating from an injected capability**: Among server-to-client **requests**, the ones originating from the injection (`window/workDoneProgress/create`; confirmed that Serena returns `MethodNotFound` — [research/serena-initialize-caps.md](research/serena-initialize-caps.md) (Japanese)) are answered successfully by lsp-det itself, not forwarded to the client. A request based on a capability the client originally declared passes straight through. A notification the client did not originally declare (progress and the like) passes straight through in v0.1, and is changed to being swallowed if a problem shows up (CC is assumed to ignore an unknown notification; to be observed)
- **Upstream vanishing**: When upstream vanishes through `exit` or a signal, an error is answered to every request the downstream side is holding, it is recorded to stderr, and lsp-det also terminates. The end of the connection (EOF) reaches downstream, and a restart is the client's decision (CC's `restartOnCrash`). No value expressing "dead" is sent (spec 8.2 item 7)

### 4.3 The Downstream Side (Standing in for the Client)

Executes the recommended behavior of spec chapter 9 on behalf of a client that does not speak the protocol. How the following **cross-workspace requests** (the same list as spec 7.0) are handled is decided by the `ServerState` above the boundary. It is reevaluated every time the state changes, and if it goes from `error` back to `ok`, it goes back to being held (`error` can recover).

| `health` \ `readiness`       | `initializing` / `indexing`            | `ready`          | `unknown`                       |
| ---------------------------- | -------------------------------------- | ---------------- | ------------------------------- |
| `ok` / `warning` / `unknown` | Hold (forwarded in order once `ready`) | Forward          | Forward (no signal to wait for) |
| `error`                      | Fail immediately                       | Fail immediately | Fail immediately                |

- `warning` is "partly functional", and since waiting does not improve it, it is treated the same as `ok` (spec chapter 9, item 5). A mapping supplements the coarseness of a language server's `warning` (5.1)
- The `error` response goes to both the held requests and any cross-workspace request that arrives while it is `error`. `ServerState`'s `message` is attached. A broken server is not hidden (spec chapter 6, item 5)
- Error codes: for `error` and for held requests at `shutdown`, LSP's `RequestFailed` (-32803, syntactically correct but the result cannot be trusted); a cancellation is `RequestCancelled` (-32800); upstream vanishing is JSON-RPC's `InternalError` (-32603, the same as when it vanishes without answering `initialize`)
- There is no time limit on holding (a non-goal in chapter 2)
- If `$/cancelRequest` points to a request being held, it is removed from the queue and answered with a `RequestCancelled` error (not sent to upstream)
- On receiving `shutdown`, every held request is answered with an error before `shutdown` flows to upstream. No request is left without a response (spec chapter 9, item 6)

**Held**:

- `textDocument/references`, `textDocument/definition`, `textDocument/typeDefinition`, `textDocument/declaration`, `textDocument/implementation`
- `workspace/symbol`
- `textDocument/prepareCallHierarchy`, `callHierarchy/incomingCalls`, `callHierarchy/outgoingCalls`
- `textDocument/rename`, `textDocument/prepareRename`

**Passed straight through (not held)**:

- Every notification (`didOpen` / `didChange` / `didSave` / `didClose` and the like. Holding one would break the server's document state)
- Single-file queries (`textDocument/documentSymbol`, `textDocument/hover`, `textDocument/completion`, the formatting family). In Rust, hover and completion can also be missing type information during `indexing`, but these are outside `coverage`'s guarantee, and waiting does not get coverage. **What the downstream side removes is only the lie in cross-workspace requests** (spec chapter 9, item 4)
- A time-constrained request (`textDocument/willSaveWaitUntil` — holding is forbidden because it blocks the save)
- Lifecycle (`initialize` / `initialized` / `shutdown` / `exit`)
- Everything in the server-to-client direction (diagnostics and the like)

#### Standing in Outside the Protocol (ADR 0015)

The downstream side also stands in for two of the client's gaps in LSP, outside the scope of this protocol. Both disappear once the client comes to do them itself.

- **Standing in for `workspace/didChangeWatchedFiles`**: When the client neither declares the capability `workspace.didChangeWatchedFiles` nor has ever sent the notification, every time a request from the 7.0 list arrives, it runs `git ls-files --cached --others --exclude-standard` at each root of `rootUri` / `workspaceFolders`, bundles the diff from the previous listing (paths and mtimes) into a single notification as Created / Changed / Deleted, sends it to upstream, and then forwards the request. No clock is used; the trigger is the request itself. No mapping is involved, and it has no per-language rule for extensions or exclusion (interpreting `.gitignore` is left to git). It does not stand in for a root outside git's management (recorded to stderr once). Once it observes the client sending the notification itself, it stops standing in from then on. If the server watches on its own, the notification doubles up, but that is harmless (measured)
- **Rewriting a duplicate `didOpen`**: Keeps the set of open uris, and rewrites a `textDocument/didOpen` for a uri that is already open into a full-text `textDocument/didChange` (`contentChanges: [{text}]`, `version` from the `didOpen`) before sending it to upstream. Done for every upstream. `text` is cut from the original byte sequence. Removed from the set on `didClose`

#### Waiting During Reindexing

Readiness is not one-way. When a branch switch or a `Cargo.toml` / `go.mod` change starts a reindex, rust-analyzer goes back to `quiescent: false` and renotifies. **The downstream side goes back to holding during this too**, to keep the guarantee "an answer that comes back is always complete" consistent across the whole session.

**Under normal edits, reindexing does not happen** ([measured](research/rust-analyzer-quiescent-measurement.md) (Japanese), ADR 0007). The substance of rust-analyzer's `quiescent` is `is_fully_ready()` (`reload.rs`), and its input `vfs_done` moves only with the VFS's batch-load progress; priming the cache is requested only around the edge where `quiescent` moves from `false` to `true`. Neither a disk write to a source file nor a `didChange` touches either of these. In the measurement too, `quiescent` never once went to `false` on a disk edit, and reflection into the index took 0.02–0.04 seconds. A `Cargo.toml` change (the positive control) round-tripped as expected, with the return to `true` taking about 250ms (a value at this workspace's scale; it does not generalize to a large project).

So the downstream side has no need for flap countermeasures (smoothing, debouncing).

### 4.4 Depth of Message Interpretation

- What the proxy interprets is only the header (`Content-Length`) and a peek at JSON's `method` / `id`. **The body is forwarded as the original bytes and never reserialized** (a full parse plus reserialize produces a change in key order and the loss of unknown fields; there is a real example of ra-multiplex dropping an unknown message with `deny_unknown_fields` — [research/proxy-implementations.md](research/proxy-implementations.md) (Japanese))
- The body is fully parsed only for: the notifications a mapping needs (`experimental/serverStatus`, `$/progress`); injecting a capability into `initialize` and reading `rootUri` / `workspaceFolders`; reading `InitializeResult`'s `serverInfo` and `serverStateProvider`; and `textDocument/didOpen`'s `uri` / `version` / `text` (for rewriting a duplicate; `text` is cut out as the original byte sequence as-is). For `workspace/didChangeWatchedFiles`, only that the client sent it is looked at; the body is not read

### 4.5 Process Lifetime and I/O

An area where prior proxies' issues cluster (→ the chapter 7 checklist).

- The upstream process is the proxy's child. It is reliably killed when the proxy exits. The proxy itself exits on the death of its parent (the client). Detecting EOF on stdin (the proxy's stdin closes if the client dies; upstream's stdin closes if the proxy dies) works as the first layer regardless of OS, and a second layer for a sudden death (`SIGKILL` and the like) is provided per OS (ADR 0012). Supported OSes are Linux, macOS, and Windows

| OS      | The proxy follows its parent's death                                                                                         | Upstream follows the proxy's death                                                                          |
| ------- | ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Linux   | `PR_SET_PDEATHSIG`                                                                                                           | `PR_SET_PDEATHSIG`                                                                                          |
| macOS   | A thread that waits on the parent pid through `kqueue`'s `EVFILT_PROC` / `NOTE_EXIT`. Kills upstream and exits once observed | No mechanism. Left to EOF on upstream's stdin (measured and recorded that the language server exits on EOF) |
| Windows | A thread that waits on the parent process's handle with `WaitForSingleObject`                                                | A Job Object's `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`                                                         |

- On the `exit` notification, `shutdown` → `exit` is propagated to upstream before it exits itself. If upstream dies first, an error is answered to held requests as in 4.2, recorded to stderr, and it exits
- stdio's `Content-Length` framing is implemented on the assumption of split arrivals and huge messages (there is a real example of ls_proxy's parse breaking on a large message being split)
- stderr relays upstream's own as-is, and the proxy's own log is mixed in with a prefix (flushed as it goes, not buffered)

### 4.6 Execution Model and Dependencies

- Three `std` threads (reading the client, reading upstream, watching the child process) + `mpsc` + a single event loop. All state stays closed inside the loop; it holds no lock
- Dependencies: `serde` / `serde_json` (peeking through `RawValue`), `thiserror`, `libc` (Linux's pdeathsig, macOS's kqueue). Only the needed functions of the Windows API (`kernel32` / `ntdll`) are declared with `extern "system"` (ADR 0012 decision C)
- tokio, rayon, and tracing are not adopted. The reasons and the conditions for reconsidering are in [adr/0005](adr/0005-runtime-and-dependencies.md) (Japanese)
- Runtime assumption: standing in for `workspace/didChangeWatchedFiles` (4.3) needs the `git` command on PATH. No crate dependency is added for it (ADR 0015)

## 5. Mappings (Adapters)

A mapping is a part of the upstream side that maps a specific language server's own vocabulary onto the server state protocol. A mapping also carries the responsibility for supplementing a language server's vocabulary's coarseness, and the downstream side looks only at the spec's values (ADR 0009 decision D-6). Once a mapping is absorbed into the server itself, the upstream side becomes the identity mapping and gets thinner. That is the final form (5.3).

### 5.1 rust-analyzer

- Maps `quiescent` in the `experimental/serverStatus` notification onto `readiness`, and `health` onto `health`. `quiescent: true` = every one of VFS loading + cargo metadata + build script + proc-macro loading + cache priming (indexing) is complete (`is_fully_ready()`, confirmed in rust-analyzer's `reload.rs`)
- Since a differential notification comes on every state transition, a `true` → `false` → `true` reindex is also tracked naturally
- **Correcting `warning`**: rust-analyzer gives `health: warning` and "Failed to discover workspace." when not even one project is found (`linked_or_discovered_projects()` and `detached_files()` both empty) (`current_status()` in `reload.rs`). Cross-workspace queries do not function in this state, so the mapping maps it to `error`. Since the only thing to distinguish it is the `message` string, this correction is fragile and is guarded by the list of tested versions (4.2). The root solution is for rust-analyzer itself to speak this protocol
- rust-analyzer's own integration tests are an implementation that "waits for `quiescent` before sending a request", the same shape as the downstream side's reference behavior (note that there is no official written completeness guarantee)

### 5.2 gopls

gopls has no vocabulary for readiness. It is synthesized from `$/progress` (`src/adapter/gopls.rs`; the grounds are gopls's source `server/general.go`, `server/workspace.go`, `server/diagnostics.go`, `progress/progress.go`).

- **readiness**: At initialization, a progress with the title "Setting up workspace" begins for each workspace folder, and ends with "Finished loading packages." after the snapshot is initialized (or, if a folder fails to load, ends with "Error loading packages: …" — it always ends, even on an error). Since the token is randomly generated, it is identified **by the title**, and once every token remembered at a begin has ended, it becomes `ready`. The same title also appears when a folder is added through `didChangeWorkspaceFolders`, so seeing a begin puts it back to `indexing` (rearming)
- **A `go.mod` change does not reissue "Setting up workspace"** (in the source it is issued nowhere but `addFolders`, and the measurement agrees). So gopls's mapping gives `indexing` only at startup and when a folder is added. During the reload after a `go.mod` change, responses keep coming back as `ready`. This is a limit of gopls's vocabulary; the root solution is for gopls itself to speak this protocol
- **health**: Once loading every folder ends with "Finished loading packages.", it is `ok` (claiming `ok` partway through would be an assertion with no observation); if it ends with "Error loading packages:", it is `error` (`ready` since the attempt is over; spec chapter 6, item 5). After that, if a progress titled "Error loading workspace" (`WorkspaceLoadFailure`) begins, it is `error` (with `message`), its report updates `message`, and once it ends with "Done.", it goes back to `ok`
- A progress arrives following a `window/workDoneProgress/create` request. This is why `window.workDoneProgress` is injected (4.2). If the client did not declare it, lsp-det answers the `create` itself
- **Guarantee**: 7.2 / 7.3 passed when run against a real gopls v0.23.0 ([measured](research/gopls-readiness-measurement.md) (Japanese)), so `{coverage: true, freshness: true}` is declared, using a list of tested versions (`adapter::gopls::TESTED_VERSIONS`) as with rust-analyzer. Since `serverInfo.version` is a JSON string of build information, the top-level `Version` is read. Nothing is declared for a version outside the range
- The reason gopls is included in v0.1 is that one mapping is needed that does more than just map an existing readiness signal — one synthesized from `$/progress`'s title. It confirms that the approach can be shown even for a language whose server has no signal of its own

### 5.3 The Future of Mappings

Having each language server absorb the judgment heuristic itself is the final form. After v0.1 is complete, a PR that implements an equivalent notification for gopls and the like, using rust-analyzer's `serverStatus` as the reference form, is considered (a scaled-down version of the path in vision.md chapter 5).

The mappings added in v0.2 ([adr/0010](adr/0010-python-typescript-mappings-for-client-adoption.md) (Japanese)), and the means of judgment for candidates beyond that, have been investigated ([research/server-readiness.md](research/server-readiness.md) (Japanese)):

- pyright (M5): `ready` on the completion of file enumeration in `window/logMessage` (info), "Found N source files" / "No source files found.". `references` walks the list of tracked files, and that list is incomplete until enumeration ends (measured: with 3001 files, `references` right after `initialize` returned 0), so this is the signal that decides the completeness of a cross-workspace request. "Starting service instance" appears per folder, so completion logs are waited for that many times. `$/progress` is the progress of analyzing opened files and is not read. `health` has no signal, so `unknown`. The start of re-enumeration, "Searching for source files", does not arrive by default at the log level, and this is recorded as a limit of pyright's vocabulary (ADR 0011 decision B). The guarantee is declared for pyright 1.1.412 and basedpyright 1.39.8, which passed 7.2 / 7.3 (`adapter::pyright::TESTED_VERSIONS` / `BASEDPYRIGHT_TESTED_VERSIONS`)
- typescript-language-server (M6, complete): `indexing` on the begin of `$/progress` (title "Initializing JS/TS language features…", derived from tsserver's `projectLoadingStart` / `projectLoadingFinish`); once every remembered token has ended, `ready` and `ok`. When tsserver goes down, `window/logMessage` (error) "[tsserver] Exited. Code:" appears and the language server survives, returning an empty array as success, so this log gives `error` (there is no restart, so it never returns). No grace period is set. Since it does not return `serverInfo`, both the log "Using Typescript version (…) X from path …" that appears before the `initialize` response and the dedicated notification `$/typescriptVersion` that appears after the response are read as what it calls itself (without the former, the guarantee at the time of the response cannot be declared). Since only the TypeScript version appears in what it calls itself, the list of tested versions is also kept by that version. Since it does not load the project until a file is opened, a client that sends only cross-workspace requests without sending `didOpen` never has its `initializing` hold released (measured)
- jdtls (out of scope): `ServiceReady` in the custom notification `language/status`

## 6. Test Strategy

- **The fake-upstream approach**: Stand up a script-based fake LSP server (`examples/fake_lsp_server.rs`, replaying things like "answer initialize → send progress → answer references") and deterministically test the logic for holding, forwarding, cancellation, an error response at `shutdown`, and reindexing
- **The upstream side's conformance tests**: A suite (`tests/conformance.rs`) that makes spec chapter 7 (server) and 8.4 (observer) executable. Includes a fake client that calls `experimental/serverState` and subscribes to the notification, with lsp-det as the first subject. Written in a form that applies as-is to a real server too (any implementation reached over LSP) — being able to say "conformant if it passes this suite" when filing a PR upstream is what makes the spec persuasive
- **The downstream side's conformance tests**: A suite (`tests/client_conformance.rs`) that makes spec 9.1 (client) executable. Stands up a conformant fake upstream, makes lsp-det the subject as the client, and verifies "waits until `ready`", "fails immediately on `error`", "proceeds on `unknown`", "does not wait outside cross-workspace requests", and "answers held requests on cancel / shutdown". When Claude Code or Serena natively support it in the future, the subject is swapped in the same suite
- Integration with a real server (rust-analyzer / gopls) is a local-only smoke test (marked `#[ignore]`). Not put into CI (avoiding flakiness; the policy of "not hiding a test failure with a workaround" does not sit well with real-server CI)
- TDD is applied (RED → GREEN → REFACTOR left in the commit history)

## 7. Pitfall Checklist from Prior Proxies

Squashed one by one during implementation. The sources are each repository's issues / source (already cloned under `reference/`).

| # | Pitfall                                                                                               | Source                                                                                    | How this design handles it                                                                                                                 |
| - | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 1 | `window/showMessage` and the like arrive **before** the `initialize` response and break the handshake | ra-multiplex #89 (the current lspmux fixed it by ignoring it, but drops the notification) | A notification during the handshake is also forwarded, in FIFO order, never dropped                                                        |

## 9. Integration Notes (Investigated Facts)

- **Claude Code**: Any command can be registered through a plugin's `.lsp.json` (the official path is the plugin only). Beyond diagnostics, CC natively uses definition / references / hover / documentSymbol / callHierarchy = a direct beneficiary of the downstream side. Has `restartOnCrash` (default true)
- **Serena**: The launch command can officially be swapped through `ls_specific_settings.<lang>.ls_path` / `ls_base_cmd` / `ls_args` (rust, python, typescript, and the like). **go is out of scope**, with `cmd="gopls"` hardcoded. But since it is resolved through PATH via the shell, spoofing PATH is possible; in that case the proxy also needs to answer a CLI call of `gopls version` (a pre-launch check requires it). Since rust-analyzer is resolved by `rustup which`, spoofing PATH does not work, and it is interposed via `ls_base_cmd` / `ls_path` instead (details in [research/serena-solidlsp.md](research/serena-solidlsp.md) (Japanese)). Since Serena itself waits up to 120 seconds for `quiescent` against rust-analyzer on its own, lsp-det takes effect through the Serena path only for gopls, which is out of scope for v0.1 ([research/serena-initialize-caps.md](research/serena-initialize-caps.md) (Japanese))
- **No existing bridge has a readiness gate at all**: cclsp does a pseudo-wait of up to 3 seconds plus a fixed 200ms sleep, mcpls parses `$/progress` and discards it, LSAP passes an empty response straight through with no wait ([research/agent-bridges.md](research/agent-bridges.md) (Japanese)). The editor side is the same: Zed does not subscribe to `serverStatus`'s `quiescent`, and no implementation exists that uses readiness to control requests ([research/zed-lsp.md](research/zed-lsp.md) (Japanese)). This behavior of Zed's is also a real example of "a client that declares but does not wait" (4.1)
