# lsp-det v0.1 設計

> LSP 拡張「サーバー状態 (Server State、拡張 S)」の参照実装となる透過プロキシ。クライアントと言語サーバーの間に挟まり、「無言の嘘」（インデックス未完了の空応答・死んだサーバーの成功風応答・編集を織り込まない応答）を消す。拡張を呼べるクライアントには `experimental/serverState` を提供し、呼べないクライアントはゲート（互換モード）で守る。最終目標は拡張の LSP 本体への提案。拡張 S の規範は [spec/extension-s-server-state.md](spec/extension-s-server-state.md)。
>
> 長期構想（3 拡張の仕様化・標準化）は [vision.md](vision.md) を、スコープ選定の理由は [adr/0001-tool-first-readiness-gate.md](adr/0001-tool-first-readiness-gate.md) を参照。本文書は v0.1 の実装スコープを定義する。

## 1. 目的と成功基準

- **利用者**: 作者自身の開発環境（Claude Code + Serena）。体制は一人・週 20h
- **成功基準**: 自分の環境で rust-analyzer と gopls がプロキシ経由で日常稼働し、準備完了の誤認による空応答がゼロになること。外部採用・標準化は成功基準に含めない
- **進め方**: 仕様（docs/spec/）が第一の成果物で、実装はそれを実証する（ADR 0003 決定 7。ADR 0001 の「仕様文書は安定稼働後」を一部改訂 — 裁定は ADR 0006）。ただし v0.1 の仕様はツールとして成立する範囲に絞る。上流提案は v0.1 が 1 ヶ月安定稼働してから再評価

### 背景となる問題

1. クライアントが `initialize` 完了直後に `textDocument/references` 等を投げる
2. サーバーはインデックス未完了のため空配列 `[]` を返す（LSP 上は合法）
3. エージェントは「参照なし」と誤認し、削除・リネーム等で壊す

LSP には「準備完了」の標準がない。機械可読な通知を持つのは rust-analyzer（`experimental/serverStatus`）と jdtls（`language/status`）のみで、形式も異なる（詳細は vision.md 6.2）。

## 2. スコープ

### やること

- 単一クライアント・単一上流の**透過プロキシ**（Rust 単一バイナリ、外部ランタイム依存なし）
- **拡張 S の surface**（→ 4.1）: `experimental/serverState` リクエスト・`experimental/serverStateChanged` 通知・保証グレード付き capability 宣言。lsp-det はこの拡張の最初の準拠実装となる
- **準拠テストスイート**: 仕様 7 節を実行可能にしたテスト群。lsp-det が最初の被験者であり、将来は実サーバーにも同じスイートを当てる（→ 6 章）
- **readiness ゲート**（→ 4.2）: 拡張を呼ばないクライアントのための互換モード。ワークスペース横断リクエストを ready まで保留してから転送
- ready 判定アダプタ: **rust-analyzer** と **gopls** の 2 つ
- Claude Code プラグイン（`.lsp.json`）としての統合

### やらないこと（明示的な非目標）

- 多重化（複数クライアント共有）。ra-multiplex の難所（ID 書き換え・capability マージ）を丸ごと回避する
- 拡張 A（宣言範囲）の合成。パーサ（tree-sitter 等）は同梱しない
- 設定ファイル・マニフェスト・レジストリ・インストーラ
- ダッシュボード等の付随機能、無制限キャッシュ
- **Linux 以外の OS**。プロセス寿命管理が `PR_SET_PDEATHSIG`（Linux 専用）に依存し、現行実装は macOS ではビルドできない（`cfg(unix)` は macOS でも真だが `libc::PR_SET_PDEATHSIG` が存在しない）。ビルドエラーで止まるのは意図的 — pdeathsig なしで静かに動くより正直な失敗。macOS 対応（kqueue の `EVFILT_PROC` 等）は v0.1 後の課題（ADR 0006 決定 5）

## 3. 起動インターフェース

argv で完結する。プロキシ独自の設定ファイルは持たない。

```text
lsp-det --adapter <name> [--gate-timeout <sec>] [--no-gate] [--gate-mode <hold|error>] -- <上流コマンド> [args...]
```

- `--adapter`: ready 判定アダプタ名（`rust-analyzer` | `gopls`）。省略時はアダプタなし（起動時ゲートなしの純透過）
- `--` 以降を上流コマンドとしてそのまま実行する
- 起動指定は呼び出し側の設定ファイル（CC の `.lsp.json`、Serena の `ls_args`）に常在させる。これが再現性の担保であり、シェルから手で起動する運用は想定しない
- 将来フラグが増えて 1 行に収まらなくなったら `--config <明示パス>` を後付けする。**暗黙のファイル探索は導入しない**

CC プラグインの `.lsp.json` 例:

```json
{
  "rust": {
    "command": "lsp-det",
    "args": ["--adapter", "rust-analyzer", "--", "rust-analyzer"],
    "extensionToLanguage": { ".rs": "rust" }
  }
}
```

## 4. 動作仕様

### 4.1 拡張 S の surface（対応クライアント向け）

プロキシは拡張 S（[spec/extension-s-server-state.md](spec/extension-s-server-state.md)）の準拠サーバーとして振る舞う。

- `InitializeResult.capabilities.experimental.serverStateProvider` に、**アダプタごとの保証グレード**を宣言して返す（rust-analyzer: `{completeness: true, freshness: true}`（準拠テスト 7.2 / 7.3 を実 rust-analyzer に当てて確認済み）、gopls: `{completeness: true}`（freshness は M3 実測後に判断）、アダプタなし: `true`（基本グレード）→ **未決**、下記）。上流の capability は置き換えず、宣言を**足す**だけにする
- `experimental/serverState` リクエストに `ServerState`（`health` + `readiness`）を応答する
- `health` または `readiness` が変わるたびに `experimental/serverStateChanged` 通知を送る
- 上流プロセスの消失（exit・シグナル）を観測したら `health: "dead"` を送出する。`dead` はサーバーの自己申告では出せない値であり、プロキシがプロセスを直接観測できることの固有価値（仕様 6.1）
- クライアントが `ClientCapabilities.experimental.serverState: true` を宣言した場合、仕様 5.2 の定義（自分で判断する意思表示）に従い**ゲート（4.2）を無効化**する

#### 未決: アダプタなしのときに何を宣言するか

本節はアダプタなしで `serverStateProvider: true`（基本グレード）を宣言するとしているが、その場合に `readiness` として何を返すかが定まらない。アダプタがないと ready 信号を観測する手段がなく、`initializing` のまま留め置けば「まだ何も答えられない」（仕様 3 章）という嘘になり、`ready` を名乗れば無言の嘘そのものになる。仕様 3 章の `readiness` に「不明」を表す値はない。

M2 の実装（PR 2）ではアダプタがある場合にのみ surface を提供し、この場合は宣言していない。**決着にはユーザーの判断と ADR が要る。** 候補:

1. アダプタなしでは宣言しない（実装の現状。純透過に徹する）
2. `health` のみを意味のある値として扱い、`readiness` に「不明」を表す第 4 の値を仕様に足す
3. アダプタなしの起動自体を廃止し、`--adapter` を必須にする

### 4.2 ゲート（非対応クライアント向けの既定動作）

`readiness` が `ready` でない間、以下の**ワークスペース横断リクエスト**（仕様 7.0 の列挙と同一）は上流に転送せず保留キューに積む。`ready` になった時点で順に転送する。`health` が `dead` になったら保留分を含む以後のリクエストに即座にエラーを応答し、沈黙でハングさせない（死を隠さない）。

ゲートの動作モード:

- `--gate-mode hold`（既定）: 上記の保留方式。クライアントの実装品質に依存せず常に完全な結果を返す
- `--gate-mode error`: 保留せず「インデックス中」を示すエラーを即座に返し、待つか進むかをクライアントに委ねる。クライアントがエラーを握りつぶして空結果に変換する場合（vscode-languageclient で確認済みの挙動）は無言の嘘に戻るため既定にしない。CC がエラーをエージェントに見せるかを M2 で実測し、既定の再判断材料とする
- `--no-gate`: ゲートを完全に無効化（純透過 + 拡張 S surface のみ）

保留対象（初期リスト。アダプタ単位で調整可能にする）:

- `textDocument/references`, `textDocument/definition`, `textDocument/typeDefinition`, `textDocument/declaration`, `textDocument/implementation`
- `workspace/symbol`
- `textDocument/prepareCallHierarchy`, `callHierarchy/incomingCalls`, `callHierarchy/outgoingCalls`
- `textDocument/rename`, `textDocument/prepareRename`

素通し（保留しない）:

- 通知すべて（`didOpen` / `didChange` / `didSave` / `didClose` 等。**保留するとサーバーの文書状態が壊れる**）
- 単一ファイルで完結する問い合わせ（`textDocument/documentSymbol`, `textDocument/hover`, `textDocument/completion`, formatting 系）
- 時間制約のあるリクエスト（`textDocument/willSaveWaitUntil` — 保存をブロックするため保留禁止）
- ライフサイクル（`initialize` / `initialized` / `shutdown` / `exit`）
- サーバー→クライアント方向すべて（diagnostics 等）

### 4.3 再インデックス中の待機

準備完了は一方通行ではない。ブランチ切り替えや `Cargo.toml` / `go.mod` 変更で再インデックスが走ると、rust-analyzer は `quiescent: false` に戻して再通知する。**この間もゲートは保留に戻る**。「返ってきた答えは常に完全」という保証をセッション全体で一貫させるため。

**通常編集では再インデックスは起きない**（[実測](research/rust-analyzer-quiescent-measurement.md)、ADR 0007）。rust-analyzer の `quiescent` の実体は `is_fully_ready()`（`reload.rs`）で、その入力である `vfs_done` は VFS の一括ロード進捗でのみ動き、キャッシュのプライミングは `quiescent` が `false` から `true` へ移る辺でしか要求されない。ソースファイルへのディスク書き込みも `didChange` も、このどちらにも触れない。実測でもディスク編集で `quiescent` は一度も `false` にならず、インデックスへの反映は 0.02〜0.04 秒だった。`Cargo.toml` の変更（陽性対照）では期待どおり往復し、`true` への復帰まで約 250ms（本ワークスペース規模での値。大規模プロジェクトには一般化できない）。

したがってゲートがフラップ対策（平滑化・デバウンス）を持つ必要はない。

追跡できないサーバー（ready 解除の信号を送らないもの）は起動時ゲートのみとし、その旨を README に明記する。

### 4.4 タイムアウトは非常口

- 通常は ready まで**無期限に**待つ。これが正常系であり、挙動は常に一貫する
- `--gate-timeout`（既定 300 秒）は「アダプタが ready 信号を取り逃したときにハングを防ぐ非常口」。発動したら保留分をそのまま転送し、**stderr に警告を出す**。発動はプロキシのバグか未知のサーバー挙動を意味する検出器であり、通常運転の一部ではない
- 保留中に `$/cancelRequest` が来たら、該当リクエストをキューから除去し、クライアントへ `RequestCancelled` エラー応答を返す（上流には送らない）

### 4.5 capability の書き換え

ready 信号はクライアントの capability 宣言に依存するため、プロキシは上流への `initialize` でクライアントの `ClientCapabilities` に以下を**追加**して転送する（他は無変更）:

- `window.workDoneProgress: true`（gopls の progress 通知に必要。未宣言だと `window/showMessage` にフォールバックしてしまう）
- `experimental.serverStatusNotification: true`（rust-analyzer。未宣言だと `experimental/serverStatus` は一切送られない）

注入した capability に由来するサーバー→クライアントの**リクエスト**は、プロキシが自ら成功応答し、クライアントへ転送しない。具体的には `window/workDoneProgress/create`（Serena は `MethodNotFound` を返すことを確認済み — [research/serena-initialize-caps.md](research/serena-initialize-caps.md)）。クライアントが元々宣言していた capability に基づくリクエストは素通しする。

クライアントが元々宣言していない通知（progress 等）がサーバーから届いた場合、クライアントへの転送可否を判断する。v0.1 では素通しし、問題が出たら握りつぶしに変更する（CC は未知の通知を無視する想定。要実測）。

### 4.6 メッセージの解釈深度

- プロキシが解釈するのはヘッダ（Content-Length）と、JSON の `method` / `id` の覗き見のみ。**ボディは原文バイトのまま転送し、再シリアライズしない**（完全パース + 再シリアライズはキー順序の変化や未知フィールドの欠落を生む。ra-multiplex が `deny_unknown_fields` で未知メッセージを落とす実例あり — [research/proxy-implementations.md](research/proxy-implementations.md)）
- readiness 追跡に必要な通知（`experimental/serverStatus`、`$/progress`）と `initialize` の capability 書き換えのみ、ボディを完全パースする

### 4.7 プロセス寿命と I/O

先行プロキシの issue 頻出領域（→ 7 章チェックリスト）。

- 上流プロセスはプロキシの子。プロキシ終了時に確実に殺す。プロキシ自身は親（クライアント）の死で終了する（Linux: `PR_SET_PDEATHSIG` + stdin EOF 検知の二重化）。`PR_SET_PDEATHSIG` は Linux 専用であり、v0.1 の対応 OS は Linux のみ（→ 2 章の非目標）
- `exit` 通知で上流に `shutdown` → `exit` を伝播してから自分も終了する。上流が先に死んだら stderr に記録してプロキシも終了する（CC 側の `restartOnCrash` に再起動を任せる）
- stdio の Content-Length フレーミングは分割到着・巨大メッセージを前提に実装する（ls_proxy に「大きなメッセージの分割でパースが壊れた」実例あり）
- stderr は上流のものをそのまま中継し、プロキシ自身のログは prefix 付きで混ぜる（バッファせず逐次フラッシュ）

### 4.8 実行モデルと依存

- std スレッド 3 本（クライアント読み・上流読み・子プロセス監視）+ `mpsc` + 単一イベントループ。全状態はループに閉じ、ロックを持たない。タイマーは `recv_timeout`
- 依存: `serde` / `serde_json`（`RawValue` による覗き見）、`thiserror`、`libc`（pdeathsig）
- tokio・rayon・tracing は採用しない。理由と再検討条件は [adr/0005](adr/0005-runtime-and-dependencies.md)

## 5. ready 判定アダプタ

### 5.1 rust-analyzer

- `experimental/serverStatus` 通知の `quiescent` を追う。`quiescent: true` = VFS ロード + cargo metadata + build script + proc-macro ロード + キャッシュプライミング（インデックス）の全完了（`is_fully_ready()`、rust-analyzer `reload.rs` で確認済み）
- 状態遷移のたびに差分通知が来るため、`true → false → true` の再インデックスも自然に追える
- rust-analyzer 自身の統合テストが「quiescent を待ってからリクエストを送る」実装であり、本設計と同型（公式の完全性保証の明文はない点に注意）

### 5.2 gopls

- `$/progress` を監視。begin の `title: "Setting up workspace"` でトークンを記憶し、その end（"Finished loading packages." / エラー時もメッセージ違いで必ず end）を ready とする（gopls `general.go` で確認済み）
- トークンはランダム生成のため **title で識別する**
- workspace folder ごとに 1 つ progress が発行される。フォルダ追加や特定の didOpen 経路でも同じ title の progress が再発行されるため、begin を観測したら ready を解除して再武装できる可能性がある（go.mod 変更時の再送有無は**要実測** — M3 の宿題）
- end は「初期ロード完了」であり診断完了ではないが、references 等の問い合わせには十分

### 5.3 アダプタの将来

判定ヒューリスティックは各言語サーバー本体に取り込ませるのが最終形。v0.1 稼働後、rust-analyzer の `serverStatus` を参照形式として gopls 等へ同等の通知を実装する PR を検討する（vision.md 5 章の経路の縮小版）。

v0.1 対象外サーバーの判定手段は調査済み（[research/server-readiness.md](research/server-readiness.md)）:

- pyright: workDoneProgress（非対応クライアントには `pyright/beginProgress` 等にフォールバック）。end は残り解析ファイル数 0 と厳密一致
- typescript-language-server: `$/progress`（`projectLoadingStart`/`Finish`）。ただしクラッシュ時も end が来るため `window/logMessage` の "Exited. Code:" と接続断の併用が必須
- jdtls: 独自通知 `language/status` の `ServiceReady`

## 6. テスト戦略

- **偽上流方式**: テスト内に台本ベースの偽 LSP サーバー（「initialize に応答 → progress を送る → references に応答」等を再生）を立て、保留・転送・キャンセル・タイムアウト・再インデックスのロジックを決定的にテストする
- **準拠テストスイート**: 仕様 7 節（グレード別準拠要件）を実行可能にしたスイートを独立した成果物として作る。`experimental/serverState` を呼び通知を購読する偽クライアントを含み、lsp-det を最初の被験者とする。**実サーバー（LSP 越しの任意の実装）にもそのまま適用できる形で書く** — 上流に PR を出す際「このスイートに通れば準拠」と言えることが仕様の説得力になる
- 実サーバー（rust-analyzer / gopls）との結合はローカル専用の smoke テスト。CI には入れない（flaky 回避。「テスト失敗を回避策で隠さない」方針と実サーバー CI は相性が悪い）
- TDD を適用する（RED → GREEN → REFACTOR をコミット履歴に残す）

## 8. マイルストーン

- **M1 — 素通しプロキシ**: ゲートなしの純透過を CC プラグイン + rust-analyzer で日常稼働させる。フレーミング・プロセス寿命・exit 伝播（チェックリスト #1, #3, #4, #5）をゲート実装の前に単体で潰す
- **M2 — 拡張 S (rust-analyzer)**: **準拠テストスイート**（仕様 7 節の実行形。中心成果物）と、それに合格する surface 実装（`experimental/serverState` / `serverStateChanged` / グレード宣言）・ServerState 追跡（readiness + health、dead のプロセス監視）・ゲート（保留キュー・キャンセル・非常口タイムアウト・再インデックス待機・dead 時の即時エラー）。実測: CC のリクエストタイムアウト、CC のエラー表示（`--gate-mode error` の既定再判断）、rust-analyzer のスナップショット方式（freshness 宣言の根拠）。quiescent フラップの実測は完了（ADR 0007。通常編集では往復しないため対策不要）
- **M3 — gopls アダプタ**: progress ヒューリスティック。go.mod 変更時の progress 再送を実測し、再武装の可否を確定
- **M4 —（v0.1 後）**: Serena 統合（`ls_base_cmd` 対応言語から。gopls は PATH 偽装 + `version` CLI 応答が必要なため最後。Serena 上流に go の DependencyProvider 化 PR を出す選択肢もある）、拡張 A の再評価、上流 PR の検討

## 9. 統合メモ（調査済みの事実）

- **Claude Code**: プラグインの `.lsp.json` で任意コマンド登録可（公式経路はプラグインのみ）。CC は diagnostics に加えて definition / references / hover / documentSymbol / callHierarchy をネイティブに使う = ゲートの直接の受益者。`restartOnCrash` あり（既定 true）
- **Serena**: `ls_specific_settings.<lang>.ls_path` / `ls_base_cmd` / `ls_args` で起動コマンドを公式に差し替え可能（rust, python, typescript 等）。**go は対象外**で `cmd="gopls"` がハードコード。ただし shell 経由 PATH 解決なので PATH 偽装は可能。その場合プロキシは `gopls version` という CLI 呼び出しにも応答する必要がある（起動前チェックが要求する）。rust-analyzer は `rustup which` で解決されるため PATH 偽装は効かず、`ls_base_cmd` / `ls_path` 経由で挟む（詳細は [research/serena-solidlsp.md](research/serena-solidlsp.md)）。なお Serena は rust-analyzer に対して自前で `quiescent` を最大 120 秒待つため、Serena 経路での lsp-det の主対象は gopls（[research/serena-initialize-caps.md](research/serena-initialize-caps.md)）
- **既存ブリッジに readiness ゲートは皆無**: cclsp は最大 3 秒の擬似待ち + 200ms 固定スリープ、mcpls は `$/progress` をパースして破棄、LSAP は待ちなしで空応答を素通し（[research/agent-bridges.md](research/agent-bridges.md)）。エディタ側も同様で、Zed は `serverStatus` の `quiescent` を購読せず、readiness をリクエスト制御に使う実装は存在しない（[research/zed-lsp.md](research/zed-lsp.md)）
