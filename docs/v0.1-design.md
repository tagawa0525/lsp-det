# lsp-det v0.1 設計

> サーバー状態プロトコル（[spec/server-state.md](spec/server-state.md)）の参照実装。クライアントと言語サーバーの間に挟まる透過プロキシで、**上流側**が言語サーバーを、**下流側**がクライアントを代行する。LSP の境界を lsp-det の中央に置き、その境界の上では常にプロトコルに準拠したやり取りが流れる。上流側は上流の語彙をプロトコルに写し、下流側はプロトコルを正しく使うクライアントとして振る舞う。どちらの側も、言語サーバー本体やクライアント本体に「足りないもの」を示す参照実装である。
>
> 長期構想（宣言範囲・起動方法の宣言を含む 3 つの仕様化）は [vision.md](vision.md) を、成功基準と構造の根拠は [adr/0009](adr/0009-success-criterion-and-two-sided-reference.md) を参照。本文書は v0.1 の実装スコープを定義する。

## 1. 目的と成功基準

- **目的**: LSP に欠けている「サーバー状態」の語彙を埋める。仕様（docs/spec/）が第一の成果物で、実装はそれを実証する（ADR 0003 決定 7、ADR 0006 決定 1）
- **成功基準**: サーバー状態プロトコルの仕様、上流側と下流側それぞれの準拠テスト、上流側と下流側の参照実装が自己無矛盾で、rust-analyzer と gopls に当てて通ること。時間条件は置かない。実サーバーへのネイティブ実装・クライアントの採用・LSP 本体への提案は順序付きの次段階（ADR 0009 決定 A）
- **観測手段**: 作者の Claude Code 環境で稼働させ、準拠テストが見落とす実サーバーの挙動を拾う。稼働そのものは成功基準ではない。観測結果は research に記録し、仕様 10 章の根拠にする。Serena 経路は v0.1 後（9 章）
- **体制**: 一人・週 20h

### 背景となる問題

1. クライアントが `initialize` 完了直後に `textDocument/references` 等を投げる
2. サーバーはインデックス未完了のため空配列 `[]` を返す（LSP 上は合法）
3. エージェントは「参照なし」と誤認し、削除・リネーム等で壊す

LSP には「準備完了」の標準がない。機械可読な通知を持つのは rust-analyzer（`experimental/serverStatus`）と jdtls（`language/status`）のみで、形式も異なる（詳細は vision.md 6.2）。

## 2. スコープ

### やること

- 単一クライアント・単一上流の**透過プロキシ**（Rust 単一バイナリ、外部ランタイム依存なし）
- **上流側**（→ 4.2）: 言語サーバーの語彙をサーバー状態プロトコルに写す。`experimental/serverState` リクエスト・`experimental/serverStateChanged` 通知・保証付き capability 宣言を、上流に代わって提供する。写像（アダプタ）は **rust-analyzer** と **gopls** の 2 つ
- **下流側**（→ 4.3）: 仕様 9 章「クライアントの推奨挙動」の参照実装。プロトコルを話さないクライアントに代わって、ワークスペース横断リクエストを `ready` まで保留する（ゲート）
- **準拠テストスイート**（→ 6 章）: 仕様 7 章（サーバー）・8.4（観測者）・9.1（クライアント）を実行可能にしたテスト群。上流側は仕様 7 章と 8.4 の、下流側は 9.1 の被験者になる。被験者を差し替えれば実サーバー・実クライアントにも当たる
- Claude Code プラグイン（`.lsp.json`）としての稼働（観測手段）

### やらないこと（明示的な非目標）

- 多重化（複数クライアント共有）。ra-multiplex の難所（ID 書き換え・capability マージ）を丸ごと回避する
- 宣言範囲（vision.md 1 章、凍結中）の合成。パーサ（tree-sitter 等）は同梱しない
- 設定ファイル・マニフェスト・レジストリ・インストーラ
- ダッシュボード等の付随機能、無制限キャッシュ
- **時間に基づく判定**。保留の打ち切りタイマー、一定時間で `ready` とみなす合成、いずれも持たない（仕様 6 章 6 項、ADR 0009 決定 D-10）。ハングの検知は外側の実クライアントのタイムアウトの責任
- **Linux 以外の OS**。プロセス寿命管理が `PR_SET_PDEATHSIG`（Linux 専用）に依存し、現行実装は macOS ではビルドできない（`cfg(unix)` は macOS でも真だが `libc::PR_SET_PDEATHSIG` が存在しない）。ビルドエラーで止まるのは意図的 — pdeathsig なしで静かに動くより正直な失敗。macOS 対応（kqueue の `EVFILT_PROC` 等）は v0.1 後の課題（ADR 0006 決定 5）

## 3. 起動インターフェース

argv で完結する。プロキシ独自の設定ファイルもフラグも持たない。

```text
lsp-det -- <上流コマンド> [args...]
```

- `--` 以降を上流コマンド（言語サーバー本体の起動コマンドライン）としてそのまま実行する
- どの写像を使うかは上流が `InitializeResult.serverInfo.name` で名乗る名前で決める（4.2）。`serverInfo` を返さないサーバー（pyright）は、起動時に自ら送る `window/logMessage` の名乗りで決める（ADR 0011）。コマンド名は見ない（ラッパースクリプト経由の起動で一致しないため）
- 起動指定は呼び出し側の設定ファイル（CC の `.lsp.json`、Serena の `ls_args`）に常在させる。これが再現性の担保であり、シェルから手で起動する運用は想定しない
- 将来フラグが必要になり 1 行に収まらなくなったら `--config <明示パス>` を後付けする。**暗黙のファイル探索は導入しない**

CC プラグインの `.lsp.json` 例（実物は `dogfood/claude-plugin/`。起動は `claude --plugin-dir dogfood/claude-plugin`。手順は `dogfood/README.md`）:

```json
{
  "rust": {
    "command": "lsp-det",
    "args": ["--", "rust-analyzer"],
    "extensionToLanguage": { ".rs": "rust" }
  }
}
```

## 4. 動作仕様

### 4.1 構造: 常に両側で動く

```text
クライアント ──[素の LSP]── 下流側 ──[LSP + サーバー状態プロトコル]── 上流側 ──[素の LSP]── 言語サーバー
                            (代行)        lsp-det 内部の境界             (写像)
```

- lsp-det は常に上流側と下流側の両方で動く。切り替えるフラグは持たない
- 上流側は、上流が自らプロトコルを宣言していれば恒等写像になる（宣言を足さず、リクエストと通知をそのまま通す）。宣言していなければ写像で上流の語彙を補い、上流に代わって宣言する
- 下流側は、下流（クライアント）が `experimental.serverState` を宣言していれば境界の上の状態を転送するだけで待たない（仕様 5.2）。宣言していなければ仕様 9 章の推奨挙動を代行する
- 上書きフラグは持たない。宣言しているのに待たないクライアントは、そのクライアントに足りないものを参照実装が示す対象であって、lsp-det が隠す対象ではない（ADR 0009 決定 D-7）

### 4.2 上流側（言語サーバーの代行）

- **capability の注入**: 写像に必要な capability を、上流への `initialize` でクライアントの `ClientCapabilities` に**追加**して転送する（他は無変更）。`serverInfo` は `initialize` の応答で分かるため、既知の写像ぶんを**無条件に**注入する。どちらも「通知を送ってよい」という許可にすぎない
  - `window.workDoneProgress: true`（gopls の progress 通知に必要。未宣言だと `window/showMessage` にフォールバックしてしまう）
  - `experimental.serverStatusNotification: true`（rust-analyzer。未宣言だと `experimental/serverStatus` は一切送られない）
  - `experimental.serverState: true`（本プロトコルの購読宣言。上流が自ら本プロトコルを話すとき、その通知を下流側が読むために要る。届いた通知はクライアントが宣言していなければクライアントへ流さない）
- **写像の選択**: 上流の `InitializeResult.serverInfo.name` で選ぶ（`"rust-analyzer"` / `"gopls"` / `"basedpyright"`。いずれもソースと実測で確認済み）。`serverInfo` がなければ、起動時に上流が自ら送る `window/logMessage` の名乗り（pyright 系の "Pyright language server 1.1.412 starting"）で選ぶ。この選択は `initialize` 応答より先に起きてよく、後から `serverInfo` が来ればそれで選び直す（ADR 0011 決定 A）。名乗りがない、または未知の名前なら写像なしで両軸 `unknown`（仕様 8.2 の 3）
- **恒等写像**: 上流の `InitializeResult` に `serverStateProvider` があれば、宣言を足さず、`experimental/serverState` を上流へ転送し、自前の通知を送らない（仕様 8.2 の 6）。このとき境界の上の状態は上流から読む。上流の通知は変化のときにしか来ないので、初期状態は lsp-det 自身が `experimental/serverState` を上流に問い合わせて得る（id は整数のクライアント id と衝突しない文字列 `lsp-det:serverState`。応答はクライアントに見せない）。応答が届くまでは「initialize 直後」の `initializing` として下流側は待つ
- **宣言**: `InitializeResult.capabilities.experimental.serverStateProvider` に、写像ごとの保証を宣言して返す。上流の capability は置き換えず、宣言を**足す**だけにする
  - rust-analyzer: `{completeness: true, freshness: true}`（準拠テスト 7.2 / 7.3 を実 rust-analyzer に当てて確認済み。rustup の 1.98.0 と nixpkgs の 2026-08-03）
  - gopls: `{completeness: true, freshness: true}`（v0.23.0 で確認済み。5.2）
  - 写像なし: `true`（保証なし）
- **テスト済みの版**: 保証は「準拠テストを通した言語サーバーの版」にだけ宣言する（仕様 8.2 の 5）。写像がその一覧（`TESTED_VERSIONS`）を持ち、`serverInfo.version` の名乗りが一覧になければ `true` に落とす。semver の範囲にしないのは、同じ rust-analyzer でも rustup の配布物は `1.98.0 (…)`、nixpkgs のビルドは `2026-08-03` と名乗り、形式が揃わないため。lsp-det は上流の内部を保証できず、テストに通ったという観測しか持たない。開発環境は `flake.nix` で固定し、`flake.lock` を更新して版が変わったら実サーバーの結合テストを通してから一覧を動かす
- **状態**: `experimental/serverState` に問い合わせ時点の `ServerState` を即答し、`health` または `readiness` が変わるたびに `experimental/serverStateChanged` を送る（下流が宣言している場合のみ）。最初の信号が届くまで `health` は `unknown`、`readiness` は「initialize 直後」に対応する `initializing`（仕様 8.2 の 2）
- **旧来の通知の透過**: rust-analyzer の `experimental/serverStatus` 等は原文のまま下流へ流す（ADR 0006 決定 4）
- **注入した capability に由来するリクエスト**: サーバー→クライアントの**リクエスト**のうち注入に由来するもの（`window/workDoneProgress/create`。Serena は `MethodNotFound` を返すことを確認済み — [research/serena-initialize-caps.md](research/serena-initialize-caps.md)）は、lsp-det が自ら成功応答し、クライアントへ転送しない。クライアントが元々宣言していた capability に基づくリクエストは素通しする。クライアントが元々宣言していない通知（progress 等）は v0.1 では素通しし、問題が出たら握りつぶしに変更する（CC は未知の通知を無視する想定。要観測）
- **上流の消失**: exit・シグナルで上流が消えたら、下流側が保留している要求すべてにエラーを応答し、stderr に記録して lsp-det も終了する。下流には接続の終了（EOF）が伝わり、再起動はクライアント（CC の `restartOnCrash`）が判断する。「死んだ」を表す値は送らない（仕様 8.2 の 7）

### 4.3 下流側（クライアントの代行）

仕様 9 章の推奨挙動を、プロトコルを話さないクライアントに代わって実行する。以下の**ワークスペース横断リクエスト**（仕様 7.0 の列挙と同一）の扱いは、境界の上の `ServerState` で決まる。状態が変わるたびに再評価し、`error` から `ok` に戻れば保留に戻る（`error` は回復しうる）。

| `health` \ `readiness`       | `initializing` / `indexing`            | `ready`      | `unknown`                  |
| ---------------------------- | -------------------------------------- | ------------ | -------------------------- |
| `ok` / `warning` / `unknown` | 保留（`ready` になった時点で順に転送） | 転送         | 転送（待つべき信号がない） |
| `error`                      | 即座にエラー                           | 即座にエラー | 即座にエラー               |

- `warning` は「部分的に機能している」であり、待っても改善しないため `ok` と同じ扱い（仕様 9 章 5 項）。言語サーバーの `warning` の粗さは写像が補う（5.1）
- `error` のエラー応答は、保留分と、`error` である間に届いた横断リクエストの両方に返す。`ServerState` の `message` を添える。壊れたサーバーを隠さない（仕様 6 章 5 項）
- エラーコード: `error` と `shutdown` 時の保留分は LSP の `RequestFailed`（-32803。構文的には正しいが結果を信頼できない）、キャンセルは `RequestCancelled`（-32800）、上流の消失は JSON-RPC の `InternalError`（-32603。`initialize` に答えず消えた場合と同じ）
- 保留に時間の上限はない（2 章の非目標）
- `$/cancelRequest` が保留中の要求を指していたら、キューから除去して `RequestCancelled` エラーを応答する（上流には送らない）
- `shutdown` を受けたら、保留分すべてにエラーを応答してから `shutdown` を上流へ流す。応答を返さない要求を作らない（仕様 9 章 6 項）

保留対象:

- `textDocument/references`, `textDocument/definition`, `textDocument/typeDefinition`, `textDocument/declaration`, `textDocument/implementation`
- `workspace/symbol`
- `textDocument/prepareCallHierarchy`, `callHierarchy/incomingCalls`, `callHierarchy/outgoingCalls`
- `textDocument/rename`, `textDocument/prepareRename`

素通し（保留しない）:

- 通知すべて（`didOpen` / `didChange` / `didSave` / `didClose` 等。**保留するとサーバーの文書状態が壊れる**）
- 単一ファイル系の問い合わせ（`textDocument/documentSymbol`, `textDocument/hover`, `textDocument/completion`, formatting 系）。Rust では hover や completion も `indexing` 中は型情報が欠けうるが、これらは `completeness` の保証対象外で、待っても完全性は得られない。**下流側が消すのは横断リクエストの嘘だけ**である（仕様 9 章 4 項）
- 時間制約のあるリクエスト（`textDocument/willSaveWaitUntil` — 保存をブロックするため保留禁止）
- ライフサイクル（`initialize` / `initialized` / `shutdown` / `exit`）
- サーバー→クライアント方向すべて（diagnostics 等）

#### 再インデックス中の待機

準備完了は一方通行ではない。ブランチ切り替えや `Cargo.toml` / `go.mod` 変更で再インデックスが走ると、rust-analyzer は `quiescent: false` に戻して再通知する。**この間も下流側は保留に戻る**。「返ってきた答えは常に完全」という保証をセッション全体で一貫させるため。

**通常編集では再インデックスは起きない**（[実測](research/rust-analyzer-quiescent-measurement.md)、ADR 0007）。rust-analyzer の `quiescent` の実体は `is_fully_ready()`（`reload.rs`）で、その入力である `vfs_done` は VFS の一括ロード進捗でのみ動き、キャッシュのプライミングは `quiescent` が `false` から `true` へ移る辺でしか要求されない。ソースファイルへのディスク書き込みも `didChange` も、このどちらにも触れない。実測でもディスク編集で `quiescent` は一度も `false` にならず、インデックスへの反映は 0.02〜0.04 秒だった。`Cargo.toml` の変更（陽性対照）では期待どおり往復し、`true` への復帰まで約 250ms（本ワークスペース規模での値。大規模プロジェクトには一般化できない）。

したがって下流側がフラップ対策（平滑化・デバウンス）を持つ必要はない。

### 4.4 メッセージの解釈深度

- プロキシが解釈するのはヘッダ（Content-Length）と、JSON の `method` / `id` の覗き見のみ。**ボディは原文バイトのまま転送し、再シリアライズしない**（完全パース + 再シリアライズはキー順序の変化や未知フィールドの欠落を生む。ra-multiplex が `deny_unknown_fields` で未知メッセージを落とす実例あり — [research/proxy-implementations.md](research/proxy-implementations.md)）
- 写像に必要な通知（`experimental/serverStatus`、`$/progress`）、`initialize` の capability 注入、`InitializeResult` の `serverInfo` と `serverStateProvider` の読み取りのみ、ボディを完全パースする

### 4.5 プロセス寿命と I/O

先行プロキシの issue 頻出領域（→ 7 章チェックリスト）。

- 上流プロセスはプロキシの子。プロキシ終了時に確実に殺す。プロキシ自身は親（クライアント）の死で終了する（Linux: `PR_SET_PDEATHSIG` + stdin EOF 検知の二重化）。`PR_SET_PDEATHSIG` は Linux 専用であり、v0.1 の対応 OS は Linux のみ（→ 2 章の非目標）
- `exit` 通知で上流に `shutdown` → `exit` を伝播してから自分も終了する。上流が先に死んだら 4.2 のとおり保留分にエラーを応答し、stderr に記録して終了する
- stdio の Content-Length フレーミングは分割到着・巨大メッセージを前提に実装する（ls_proxy に「大きなメッセージの分割でパースが壊れた」実例あり）
- stderr は上流のものをそのまま中継し、プロキシ自身のログは prefix 付きで混ぜる（バッファせず逐次フラッシュ）

### 4.6 実行モデルと依存

- std スレッド 3 本（クライアント読み・上流読み・子プロセス監視）+ `mpsc` + 単一イベントループ。全状態はループに閉じ、ロックを持たない
- 依存: `serde` / `serde_json`（`RawValue` による覗き見）、`thiserror`、`libc`（pdeathsig）
- tokio・rayon・tracing は採用しない。理由と再検討条件は [adr/0005](adr/0005-runtime-and-dependencies.md)

## 5. 写像（アダプタ）

写像は上流側の部品で、特定の言語サーバー固有の語彙をサーバー状態プロトコルに写す。言語サーバーの語彙の粗さを補う責任も写像が持ち、下流側は仕様の値だけを見る（ADR 0009 決定 D-6）。写像がサーバー本体に取り込まれれば上流側は恒等写像になり薄くなる。それが最終形である（5.3）。

### 5.1 rust-analyzer

- `experimental/serverStatus` 通知の `quiescent` を `readiness` に、`health` を `health` に写す。`quiescent: true` = VFS ロード + cargo metadata + build script + proc-macro ロード + キャッシュプライミング（インデックス）の全完了（`is_fully_ready()`、rust-analyzer `reload.rs` で確認済み）
- 状態遷移のたびに差分通知が来るため、`true → false → true` の再インデックスも自然に追える
- **`warning` の補正**: rust-analyzer はプロジェクトが 1 つも見つからないとき（`linked_or_discovered_projects()` と `detached_files()` が共に空）に `health: warning` と "Failed to discover workspace." を出す（`reload.rs` の `current_status()`）。この状態では横断問い合わせは機能しないので、写像は `error` に写す。判別材料は `message` の文字列しかないため、この補正は脆く、テスト済みの版の一覧（4.2）で守る。根本の解決は rust-analyzer 側が本プロトコルを話すこと
- rust-analyzer 自身の統合テストが「quiescent を待ってからリクエストを送る」実装であり、下流側の参照挙動と同型（公式の完全性保証の明文はない点に注意）

### 5.2 gopls

gopls は readiness の語彙を持たない。`$/progress` から合成する（`src/adapter/gopls.rs`。根拠は gopls のソース `server/general.go`・`server/workspace.go`・`server/diagnostics.go`・`progress/progress.go`）。

- **readiness**: 初期化時にワークスペースフォルダごとに title "Setting up workspace" の progress が begin し、スナップショットの初期化後に "Finished loading packages." で end する（フォルダのロード失敗なら "Error loading packages: …" で end。エラーでも必ず end する）。トークンはランダム生成なので **title で識別**し、begin で覚えたトークンがすべて end したら `ready`。同じ title は `didChangeWorkspaceFolders` でフォルダが足されたときにも出るので、begin を見たら `indexing` に戻す（再武装）
- **go.mod の変更では "Setting up workspace" は再発行されない**（ソース上、`addFolders` 以外に発行箇所がなく、[実測](research/gopls-readiness-measurement.md)でも一致）。したがって gopls の写像は起動時とフォルダ追加時にだけ `indexing` を出す。go.mod 変更後の再ロード中の応答は `ready` のまま返る。これは gopls の語彙の限界であり、根本の解決は gopls 側が本プロトコルを話すこと
- **health**: 全フォルダのロードが "Finished loading packages." で終わったら `ok`（途中で `ok` を名乗るのは観測なしの主張）、"Error loading packages:" で終わったら `error`（試行は終わったので `ready`。仕様 6 章 5 項）。その後は title "Error loading workspace"（`WorkspaceLoadFailure`）の progress が begin したら `error`（message 付き）、report で message を更新、"Done." で end したら `ok` に戻る
- progress は `window/workDoneProgress/create` リクエストに続いて届く。`window.workDoneProgress` を注入しているのはこのため（4.2）。クライアントが宣言していなければ lsp-det が create に自ら応答する
- **保証**: 7.2 / 7.3 を実 gopls v0.23.0 に当てて通った（[実測](research/gopls-readiness-measurement.md)）ので、rust-analyzer と同じくテスト済みの版の一覧（`adapter::gopls::TESTED_VERSIONS`）で `{completeness: true, freshness: true}` を宣言する。`serverInfo.version` はビルド情報の JSON 文字列なので、最上位の `Version` を読む。範囲外の版には宣言しない
- gopls を v0.1 に含める理由は、既存の readiness 信号を写すだけでない写像（`$/progress` の title からの合成）が 1 つ要ることにある。サーバー本体に信号がない言語にも示せることを確かめる

### 5.3 写像の将来

判定ヒューリスティックは各言語サーバー本体に取り込ませるのが最終形。v0.1 完了後、rust-analyzer の `serverStatus` を参照形式として gopls 等へ同等の通知を実装する PR を検討する（vision.md 5 章の経路の縮小版）。

v0.2 で足す写像（[adr/0010](adr/0010-python-typescript-mappings-for-client-adoption.md)）と、その先の候補の判定手段は調査済み（[research/server-readiness.md](research/server-readiness.md)）:

- pyright（M5）: `window/logMessage`（info）のファイル列挙完了 "Found N source files" / "No source files found." で `ready`。references は追跡中のファイル一覧を走査し、その一覧は列挙が終わるまで不完全なので（[実測](research/pyright-readiness-measurement.md): 3001 ファイルで `initialize` 直後の references は 0 件）、これが横断リクエストの完全性を決める信号である。フォルダごとに "Starting service instance" が出るので、その数だけ完了ログを待つ。`$/progress` は開いたファイルの解析の進行であり読まない。health は信号がなく `unknown`。再列挙の開始 "Searching for source files" は log レベルで既定では届かず、これは pyright の語彙の限界として記録する（ADR 0011 決定 B）
- typescript-language-server（M6）: `$/progress`（tsserver の `projectLoadingStart` / `projectLoadingFinish` イベントに由来。capability `window.workDoneProgress` を宣言しないクライアントには何も出ない）。ただしクラッシュ時も end が来るため `window/logMessage` の "Exited. Code:" で health を `error` にする。logMessage が end より後にしか来ないなら接続の終了（EOF）で伝わる。猶予時間は置かない（時間判定の禁止）
- jdtls（範囲外）: 独自通知 `language/status` の `ServiceReady`

## 6. テスト戦略

- **偽上流方式**: 台本ベースの偽 LSP サーバー（`examples/fake_lsp_server.rs`。「initialize に応答 → progress を送る → references に応答」等を再生）を立て、保留・転送・キャンセル・`shutdown` 時のエラー応答・再インデックスのロジックを決定的にテストする
- **上流側の準拠テスト**: 仕様 7 章（サーバー）と 8.4（観測者）を実行可能にしたスイート（`tests/conformance.rs`）。`experimental/serverState` を呼び通知を購読する偽クライアントを含み、lsp-det を最初の被験者とする。**実サーバー（LSP 越しの任意の実装）にもそのまま適用できる形で書く** — 上流に PR を出す際「このスイートに通れば準拠」と言えることが仕様の説得力になる
- **下流側の準拠テスト**: 仕様 9.1（クライアント）を実行可能にしたスイート（`tests/client_conformance.rs`）。プロトコルに準拠した偽上流を立て、lsp-det をクライアントとして被験者にし、「`ready` まで待つ」「`error` で即失敗」「`unknown` で進む」「横断以外は待たない」「cancel / shutdown で保留分に応答する」を検証する。将来 Claude Code や Serena がネイティブ対応したとき、同じスイートで被験者を差し替える
- 実サーバー（rust-analyzer / gopls）との結合はローカル専用の smoke テスト（`#[ignore]` 付き）。CI には入れない（flaky 回避。「テスト失敗を回避策で隠さない」方針と実サーバー CI は相性が悪い）
- TDD を適用する（RED → GREEN → REFACTOR をコミット履歴に残す）

## 9. 統合メモ（調査済みの事実）

- **Claude Code**: プラグインの `.lsp.json` で任意コマンド登録可（公式経路はプラグインのみ）。CC は diagnostics に加えて definition / references / hover / documentSymbol / callHierarchy をネイティブに使う = 下流側の直接の受益者。`restartOnCrash` あり（既定 true）
- **Serena**: `ls_specific_settings.<lang>.ls_path` / `ls_base_cmd` / `ls_args` で起動コマンドを公式に差し替え可能（rust, python, typescript 等）。**go は対象外**で `cmd="gopls"` がハードコード。ただし shell 経由 PATH 解決なので PATH 偽装は可能。その場合プロキシは `gopls version` という CLI 呼び出しにも応答する必要がある（起動前チェックが要求する）。rust-analyzer は `rustup which` で解決されるため PATH 偽装は効かず、`ls_base_cmd` / `ls_path` 経由で挟む（詳細は [research/serena-solidlsp.md](research/serena-solidlsp.md)）。Serena は rust-analyzer に対して自前で `quiescent` を最大 120 秒待つため、Serena 経路で lsp-det が効くのは gopls だけであり、v0.1 の範囲外（[research/serena-initialize-caps.md](research/serena-initialize-caps.md)）
- **既存ブリッジに readiness ゲートは皆無**: cclsp は最大 3 秒の擬似待ち + 200ms 固定スリープ、mcpls は `$/progress` をパースして破棄、LSAP は待ちなしで空応答を素通し（[research/agent-bridges.md](research/agent-bridges.md)）。エディタ側も同様で、Zed は `serverStatus` の `quiescent` を購読せず、readiness をリクエスト制御に使う実装は存在しない（[research/zed-lsp.md](research/zed-lsp.md)）。Zed のこの挙動は「宣言するが待たないクライアント」の実例でもある（4.1）
